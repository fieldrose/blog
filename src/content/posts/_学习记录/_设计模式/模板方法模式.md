## 模板方法模式

模板方法模式在一个方法中定义算法的骨架，把某些步骤推迟到子类实现。骨架方法固定调用顺序，子类只填充可变部分，调用方看到的是一个完整的流程。

### 1. 定义与组成

模式由三部分构成：

- 抽象父类：声明模板方法与各步骤方法的签名，给出通用步骤的默认实现。
- 具体子类：覆盖需要变化的步骤方法，不改变调用顺序。
- 模板方法：通常命名为 `init`、`run`、`prepare`，按固定顺序调用步骤，一般不允许子类覆盖。

与策略模式的差别在于控制权的归属。策略模式把整个算法替换掉，调用方选择策略；模板方法保留算法结构，只让子类替换其中几步，调用方只调用模板方法。

模板方法的收益是把「流程」与「步骤实现」分离。流程只写一次，步骤可以有多个版本；代价是继承带来的耦合，父类改动会传导到所有子类。

### 2. Coffee or Tea

咖啡与茶的冲泡流程结构相同，差异集中在两处：冲泡方式与调料。

| 步骤 | 咖啡 | 茶 |
| --- | --- | --- |
| 烧水 | 相同 | 相同 |
| 冲泡 | 用沸水冲咖啡粉 | 用沸水泡茶叶 |
| 倒入杯中 | 相同 | 相同 |
| 加调料 | 加糖与牛奶 | 加柠檬 |

把相同步骤上移到父类，不同步骤留给子类：

```js
class Beverage {
  prepare() {
    this.boilWater();
    this.brew();
    this.pourInCup();
    this.addCondiments();
  }

  boilWater() {
    console.log("boil water");
  }

  pourInCup() {
    console.log("pour into cup");
  }

  brew() {
    throw new Error("subclass must implement brew");
  }

  addCondiments() {}
}

class Coffee extends Beverage {
  brew() {
    console.log("drip coffee through filter");
  }

  addCondiments() {
    console.log("add sugar and milk");
  }
}

class Tea extends Beverage {
  brew() {
    console.log("steep tea leaves");
  }

  addCondiments() {
    console.log("add lemon");
  }
}
```

`prepare` 是模板方法，`boilWater` 与 `pourInCup` 是通用步骤，`brew` 是必须实现的步骤，`addCondiments` 是可选步骤。子类只关心自己负责的两步。

### 3. JavaScript 中的实现

#### 3.1 原型继承

ES6 之前用构造函数与原型链模拟继承：

```js
function Beverage() {}

Beverage.prototype.prepare = function () {
  this.boilWater();
  this.brew();
  this.pourInCup();
  this.addCondiments();
};

Beverage.prototype.boilWater = function () {
  console.log("boil water");
};

Beverage.prototype.pourInCup = function () {
  console.log("pour into cup");
};

Beverage.prototype.brew = function () {
  throw new Error("subclass must implement brew");
};

Beverage.prototype.addCondiments = function () {};

function Coffee() {}

Coffee.prototype = Object.create(Beverage.prototype);
Coffee.prototype.constructor = Coffee;

Coffee.prototype.brew = function () {
  console.log("drip coffee through filter");
};

Coffee.prototype.addCondiments = function () {
  console.log("add sugar and milk");
};
```

- `Object.create(Beverage.prototype)` 建立原型链，子类未覆盖的方法回落到父类实现。
- 覆盖 `constructor` 是原型继承的通用约定，与模式本身无关，遗漏时 `instanceof` 仍然正确，但 `constructor` 指向会出错。
- 父类的 `brew` 抛错充当抽象方法，子类忘记实现时在首次调用即暴露。

#### 3.2 class 版本

`class` 与 `extends` 是原型继承的语法封装，语义一致：

```js
class Beverage {
  prepare() {
    this.boilWater();
    this.brew();
    this.pourInCup();
    this.addCondiments();
  }

  boilWater() {
    console.log("boil water");
  }

  pourInCup() {
    console.log("pour into cup");
  }

  brew() {
    throw new Error("subclass must implement brew");
  }

  addCondiments() {}
}

class Coffee extends Beverage {
  brew() {
    console.log("drip coffee through filter");
  }
}
```

子类需要调用父类逻辑时使用 `super`，例如在通用步骤前后追加日志：

```js
class Espresso extends Beverage {
  brew() {
    console.log("preheat cup");
    super.brew();
  }
}
```

#### 3.3 无抽象类的变通

JavaScript 没有编译期抽象方法，三种常见替代：

| 手段 | 检查时机 | 说明 |
| --- | --- | --- |
| 父类方法抛错 | 运行时 | 实现简单，错误在首次调用时出现 |
| TypeScript `abstract` | 编译期 | 需要类型系统支持，构建阶段拦截 |
| 文档与测试约定 | 无自动检查 | 依赖单元测试覆盖每个子类 |

```ts
abstract class Beverage {
  prepare(): void {
    this.boilWater();
    this.brew();
    this.pourInCup();
    this.addCondiments();
  }

  protected abstract brew(): void;
  protected abstract addCondiments(): void;

  protected boilWater(): void {
    console.log("boil water");
  }
}
```

TypeScript 的 `abstract` 只约束类型，运行时仍是普通方法；需要运行时兜底时，仍在基类中保留抛错实现。

### 4. 使用场景与钩子方法

模板方法的适用信号是「流程固定、步骤可变」：

- 框架生命周期：`created`、`mounted`、`updated` 由框架按固定顺序调用，业务填充内容。
- 构建流水线：安装依赖、类型检查、打包、产物校验，顺序固定，每步实现因项目而异。
- 数据处理管道：读取、校验、转换、写入，读取源与目标格式变化，中间流程不变。
- 表单提交：校验、序列化、请求、结果处理，校验规则与请求地址由具体表单决定。

钩子方法（hook）用于控制可选步骤是否执行。父类给出默认返回值的判断方法，子类按需覆盖：

```js
class Beverage {
  prepare() {
    this.boilWater();
    this.brew();
    this.pourInCup();

    if (this.customerWantsCondiments()) {
      this.addCondiments();
    }
  }

  customerWantsCondiments() {
    return true;
  }

  addCondiments() {}
}

class BlackCoffee extends Beverage {
  customerWantsCondiments() {
    return false;
  }
}
```

钩子把「是否执行」的判断放在子类，模板方法只负责读取结果。相比在模板方法里写 `if (this.type === "black")`，钩子避免了父类对具体类型的感知。

### 5. 好莱坞原则

「Don't call us, we'll call you.」子类不主动调用父类流程，父类在骨架中调用子类实现的步骤。控制权反转，子类只提供实现，不决定何时执行。

- 与依赖倒置的区别：好莱坞原则描述调用方向，依赖倒置描述依赖关系应指向抽象。
- JavaScript 中，回调、事件监听、生命周期钩子都是这一原则的体现：框架调用业务代码，业务代码不反向调用框架内部。
- 违反原则的典型症状是子类在构造阶段主动调用父类的模板方法，导致父类尚未完成初始化就被执行流程。

框架设计中，模板方法把「何时调用」收归框架，把「调用时做什么」交给使用方，插件系统与中间件机制都建立在这一分工上。

### 6. 是否真的需要继承

继承实现模板方法的成本：

- 单一继承链：子类只能继承一个父类，父类职责一多就难以拆分。
- 传导性：父类修改步骤顺序或签名，所有子类同时受影响。
- 隐式契约：子类必须知道哪些方法可以覆盖、哪些不能，缺少语法约束时容易误改模板方法。

替代方案一，高阶函数把步骤作为参数传入：

```js
function prepareBeverage({ brew, addCondiments }) {
  console.log("boil water");
  brew();
  console.log("pour into cup");
  addCondiments();
}

prepareBeverage({
  brew: () => console.log("drip coffee through filter"),
  addCondiments: () => console.log("add sugar and milk"),
});
```

替代方案二，把步骤组成数组顺序执行：

```js
const steps = [
  () => console.log("boil water"),
  () => console.log("drip coffee through filter"),
  () => console.log("pour into cup"),
  () => console.log("add sugar and milk"),
];

steps.forEach((step) => step());
```

| 方式 | 适用条件 | 限制 |
| --- | --- | --- |
| 继承 | 子类共享大量默认实现，步骤集合稳定 | 单一继承链，父类变更影响面大 |
| 高阶函数 | 步骤数量少，调用点固定 | 步骤组合多时参数列表膨胀 |
| 组合数组 | 步骤可动态增删 | 需要额外的上下文传递机制 |

继承仍然适合框架层：默认实现多、子类数量可观、需要 `super` 复用父类逻辑。业务代码中的一次性流程，用函数参数化步骤更直接，也避免了为「模板」专门维护一条继承链。

模板方法的核心是「固定顺序 + 可变步骤」，继承只是实现手段之一。把流程写成一个普通函数，把可变部分作为参数或回调传入，同样满足模式的意图。
