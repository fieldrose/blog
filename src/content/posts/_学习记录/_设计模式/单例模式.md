## 单例模式

单例保证一个类只有一个实例，并提供访问该实例的统一入口。JavaScript 中单例不需要类来完成，闭包、模块作用域、`Proxy` 都能承担控制职责。判断单例是否用对，取决于实例的唯一性是否真的需要，而不是代码是否写得像 GoF 原著。

### 1. 实现单例

#### 1.1 需求与朴素实现

登录弹窗在全站只有一份：重复创建会带来 DOM 节点叠加、遮罩层错位、表单状态分叉。最直接的写法是模块内维护一个实例变量：

```js
class LoginModal {
  constructor() {
    this.visible = false;
  }

  show() {
    this.visible = true;
  }

  hide() {
    this.visible = false;
  }
}

let instance = null;

function getLoginModal() {
  if (!instance) {
    instance = new LoginModal();
  }
  return instance;
}

getLoginModal() === getLoginModal(); // true
```

- 实例只在首次调用时创建，后续调用返回同一引用。
- 创建逻辑集中在一处，便于加入初始化参数与埋点。
- 是否存在第二个实例，完全依赖调用方遵守「不要直接 `new`」的约定。

#### 1.2 缺陷：不透明与耦合

```js
// Another module can still bypass the accessor
const modal = new LoginModal();
```

- 调用方需要先知道有 `getLoginModal` 这个入口，`new LoginModal()` 在语法上依然合法，约定被打破时没有任何报错。
- 单例控制与业务逻辑写在同一个模块里，删除单例需求时需要同时改动类与所有调用点。
- 隐式全局状态让测试用例之间相互污染，前一个用例打开的弹窗会影响后一个用例的断言。
- 依赖关系不可见，阅读 `LoginModal` 的代码无法判断它是否是单例。

### 2. 透明的单例

#### 2.1 闭包隐藏实例

「透明」指调用方仍然使用 `new`，不需要记住额外的访问函数。用立即执行函数把实例封在闭包里，对外的构造入口改成返回实例的普通函数：

```js
const LoginModal = (function () {
  let instance = null;

  function Modal() {
    this.visible = false;
  }

  Modal.prototype.show = function () {
    this.visible = true;
  };

  Modal.prototype.hide = function () {
    this.visible = false;
  };

  return function () {
    if (!instance) {
      instance = new Modal();
    }
    return instance;
  };
})();

new LoginModal() === new LoginModal(); // true
```

- 调用形态与普通构造器一致，`new` 之后拿到的始终是同一对象。
- 实例无法从外部取得，`Modal` 构造器没有暴露到作用域外。
- 每次 `new` 都会执行返回函数，但 `instance` 已经存在，构造函数体只执行一次。

#### 2.2 代价

- 构造函数与单例控制合并，`LoginModal` 不再是可独立实例化的类，测试时无法创建隔离的副本。
- `instanceof` 的语义被破坏：返回对象由内部 `Modal` 构造，`new LoginModal() instanceof LoginModal` 为 `false`，需要手动修补 `prototype`。
- 全局状态被包装得更隐蔽，调用方看不出背后共享了状态，模块间依赖仍然存在。
- 类型声明会变得别扭：返回值类型是 `Modal` 实例，但 `LoginModal` 本身是函数而非类。

### 3. 用代理实现单例

#### 3.1 职责分离

单例控制属于「创建阶段」的职责，可以抽到代理层；本体只负责自身业务，仍然是一个正常的类，可以 `new`、可以被继承、可以在测试中直接实例化。调用方通过代理访问，拿到的是被约束后的创建入口。

#### 3.2 代码

```js
class LoginModal {
  constructor() {
    this.visible = false;
  }

  show() {
    this.visible = true;
  }
}

function createSingleton(Target) {
  let instance = null;

  return new Proxy(Target, {
    construct(target, args) {
      if (!instance) {
        instance = Reflect.construct(target, args);
      }
      return instance;
    },
  });
}

const LoginModalProxy = createSingleton(LoginModal);

new LoginModalProxy() === new LoginModalProxy(); // true
new LoginModalProxy() instanceof LoginModal; // true
```

- `construct` 陷阱拦截 `new` 操作，是否复用实例由代理决定。
- 本体不感知单例，单例策略可以移除、替换，也可以对不同类复用同一个工厂。
- `Reflect.construct` 保留 `new.target` 语义，派生类继承时行为正确。
- 代理与原类同型，`instanceof` 判定成立，类型系统也能接受。

### 4. JavaScript 中的单例

#### 4.1 全局变量与命名空间

单例最原始的实现是全局变量。直接挂在全局对象上会与第三方脚本冲突，历史上用命名空间对象收敛：

```js
window.App = window.App || {};
App.modal = App.modal || new LoginModal();
```

- 命名空间只是把冲突面从顶层压缩到单一键，没有解决全局可变状态的根本问题。
- `App.modal` 可被任意脚本覆盖，初始化顺序依赖脚本加载顺序。
- 模块化之后，全局命名空间的用法基本退出，`ES Module` 提供了作用域隔离。

#### 4.2 惰性单例

惰性单例把实例创建推迟到首次使用。页面加载阶段创建全部单例会拉长首屏时间，而多数单例在首屏并不需要。

```js
const getModal = (function () {
  let instance = null;

  return function () {
    if (!instance) {
      instance = new LoginModal();
    }
    return instance;
  };
})();
```

- 未调用 `getModal` 时不存在实例，也不存在相关的 DOM 与事件监听。
- 判断条件常用 `instance === null`，若创建函数可能返回 `0`、`""`、`false` 等假值，需要用独立的布尔标记。

#### 4.3 通用惰性单例

把「只创建一次」与「创建什么」拆开，单例逻辑可以复用：

```js
function getSingle(factory) {
  let result = null;

  return function (...args) {
    if (result) {
      return result;
    }
    result = factory.apply(this, args);
    return result;
  };
}

const createIframe = getSingle(() => {
  const iframe = document.createElement("iframe");
  iframe.style.display = "none";
  document.body.appendChild(iframe);
  return iframe;
});
```

- 通用包装只关心调用次数，工厂负责具体创建，两者独立变化。
- 首次调用之后 `result` 恒为真值，后续参数会被忽略；需要按参数区分实例时不适合该包装。
- 该结构在需要复用单个编辑器实例、单个地图容器时使用较多。

#### 4.4 ES Module 的单例语义

```js
// store.js
export const store = {
  count: 0,
};

export function increment() {
  store.count += 1;
}
```

```js
// a.js
import { store, increment } from "./store.js";

increment();
store.count; // 1
```

- 模块在首次被导入时求值一次，导出对象在所有导入方之间共享，天然满足单例定义。
- 打包工具的重复导入会被去重，不会产生第二份模块实例。
- 顶层副作用（读取 `localStorage`、注册全局监听）只在首次导入时执行，导入顺序会决定执行时机。
- 循环依赖时，先被求值的模块可能拿到尚未完成初始化的导出，表现为 `undefined`，单例的初始化逻辑应避免依赖导入顺序。

#### 4.5 实际场景

| 场景 | 单例承担的状态 | 风险点 |
| --- | --- | --- |
| 全局弹窗、通知队列 | 当前弹窗栈、队列 | 多个功能同时争用，需要明确的排队规则 |
| 配置中心 | 运行时配置 | 配置变更需要通知机制，否则读取方拿到旧值 |
| 日志上报器 | 缓冲区、上报队列 | 页面卸载时缓冲区可能丢失，需要 `sendBeacon` |
| 请求客户端 | 拦截器、`baseURL` | 不同业务线需要不同配置时，应改为工厂而非单例 |
| 微前端共享状态 | 跨应用通信总线 | 宿主与子应用的生命周期不一致，需要显式销毁 |

- 单例的收益是省去重复初始化与状态同步成本，代价是引入隐式全局状态。
- 判断标准：全局唯一是业务约束（如页面只有一个播放器），还是仅为了避免传参（如表单校验器）。后者应改为显式注入。
- 微前端与浏览器扩展中跨边界共享单例时，需要把实例挂到 `window` 或独立的共享模块，并约定销毁时机。
