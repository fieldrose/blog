## 享元模式

享元模式（Flyweight）面向性能：当系统中存在大量相似对象时，把对象中不随环境变化的部分抽取为共享实例，避免重复创建。模式不会减少对象承载的数据量，减少的是重复数据的份数。

### 1. 初识享元

前端场景中，大量相似对象的来源很具体：一个列表渲染上千行、地图上散布数万个标记、富文本编辑器里每个字符一个对象、上传队列里每个文件一个实例。这些对象的字段往往只有少部分是每次不同的，其余完全一致。

```js
function Marker(type, icon, color, x, y) {
  this.type = type;
  this.icon = icon;
  this.color = color;
  this.x = x;
  this.y = y;
}

// 2000 instances, each carrying the same icon and color
const markers = points.map((p) => new Marker("poi", "pin.svg", "#f00", p.x, p.y));
```

`type`、`icon`、`color` 在 2000 个实例中完全相同，`x`、`y` 才是每个标记独有的数据。享元把前者提取为共享对象，后者在使用时传入。

适用前提需要同时满足：

- 对象数量大到产生内存或 GC 压力。
- 对象中存在可枚举、可复用的相同部分。
- 创建成本高于查表成本。

数量不足时，引入工厂与缓存带来的复杂度超过收益。

### 2. 内部状态与外部状态

享元把对象字段分成两类：

| 类型 | 定义 | 归属 | 示例 |
| --- | --- | --- | --- |
| 内部状态 | 不随环境变化，可被多个场景共享 | 享元对象自身 | 上传地址、图标、字体样式 |
| 外部状态 | 随场景变化，每次使用不同 | 调用方持有，使用时传入 | 文件名、文件大小、坐标 |

划分标准是「是否会因调用而变化」。内部状态一旦确定就不再修改，享元对象因此在生命周期内保持不可变；外部状态不进入享元对象，避免并发使用时互相覆盖。

归属的取舍直接影响共享粒度：

- 把外部状态塞进内部，共享对象就变成一次性的，缓存命中率降为零。
- 把内部状态外置，每次调用都要重复传参，调用方负担上升，也容易传错。
- 边界模糊时，以「同一时刻是否可能被两个调用方以不同值使用」来判断：可能，就必须外置。

### 3. 通用结构

享元的标准结构是一个带缓存的工厂：按 key 查找，未命中才创建。

```js
function FlyweightFactory() {
  const cache = new Map();

  return {
    get(key, create) {
      if (!cache.has(key)) {
        cache.set(key, create());
      }
      return cache.get(key);
    },
    size() {
      return cache.size;
    },
  };
}

const factory = FlyweightFactory();
const a = factory.get("poi-red", () => ({ icon: "pin.svg", color: "#f00" }));
const b = factory.get("poi-red", () => ({ icon: "pin.svg", color: "#f00" }));

console.log(a === b); // true
```

- `key` 必须唯一确定内部状态的组合，否则会把不同配置的对象错误地合并。
- 缓存在模块作用域内长期存在，key 空间需要有界，否则缓存本身成为内存增长点。
- 工厂返回的共享对象应视为只读，调用方修改其字段会污染所有使用者。

key 的构造方式常见两种：把内部状态拼接成字符串，或用嵌套 `Map` 逐层索引。字符串拼接简单，但字段含分隔符时需要转义；嵌套 `Map` 避免了拼接歧义，代价是代码行数增加。

### 4. 文件上传示例

初版实现按文件逐个创建上传器：

```js
function Uploader(uploadType, url, fileName, fileSize) {
  this.uploadType = uploadType;
  this.url = url;
  this.fileName = fileName;
  this.fileSize = fileSize;
}

Uploader.prototype.start = function () {
  console.log("upload", this.fileName, "to", this.url);
};

files.forEach((file) => {
  const uploader = new Uploader("image", "/api/upload", file.name, file.size);
  uploader.start();
});
```

200 个文件意味着 200 份 `uploadType` 与 `url`。这些字段由上传控件统一配置，同一次批量上传中完全一致。

重构为享元：把配置类字段留在共享对象，文件名与大小作为参数传入。

```js
function Uploader(uploadType, url) {
  this.uploadType = uploadType;
  this.url = url;
}

Uploader.prototype.start = function (fileName, fileSize) {
  console.log("upload", fileName, fileSize, "to", this.url);
};

const uploaderFactory = (function () {
  const cache = new Map();

  return {
    create(uploadType, url) {
      const key = `${uploadType}::${url}`;

      if (!cache.has(key)) {
        cache.set(key, new Uploader(uploadType, url));
      }

      return cache.get(key);
    },
  };
})();

function addFile(uploadType, url, file) {
  const uploader = uploaderFactory.create(uploadType, url);
  uploader.start(file.name, file.size);
}
```

收益可以量化：实例数量从「文件数」降为「上传类型 × 上传地址」的组合数。单次批量上传中，这个组合数通常是 1，200 个文件只对应 1 个上传器实例。

代价同时出现：

- 每次调用都要传外部状态，`start` 的参数列表变长。
- 共享对象不能保存与单次请求相关的字段。若在 `start` 中写 `this.fileName = fileName`，并发上传时后一个文件会覆盖前一个，日志与进度全部错位。
- 若确实需要在共享对象上暂存单次状态，只能改为「外部状态对象 + 由调用方持有」，此时共享对象又退化为无状态工具，收益需要重新核算。

判断是否重构的依据是实例的字段构成，而不是文件数量。配置字段占比高、实例数量大时，享元有效；每个实例的字段几乎都不同（如图片裁剪参数、逐帧动画数据），共享无从谈起。

### 5. 适用性与代价

| 维度 | 表现 |
| --- | --- |
| 内存 | 重复数据只保留一份，实例数下降 |
| GC | 对象创建频率降低，回收压力减小 |
| 复杂度 | 引入工厂、缓存与外部状态传递 |
| 缓存 | key 无界时自身成为内存泄漏源 |
| 可读性 | 共享对象无状态，业务逻辑需显式传参 |

适用场景集中在「数量大 + 部分字段相同」：

- 文本编辑器把每个字符的字体、字号、颜色抽成共享样式对象，字符位置与内容作为外部状态。
- 地图把图标、线型共享，坐标作为外部状态。
- 表格把单元格样式共享，单元格值与坐标作为外部状态。

不适用的情况同样明确：对象数量在数百以内、字段几乎全不相同、共享对象需要频繁修改内部状态。这几种情况下，普通的对象创建更直接，缓存反而增加维护成本。

享元与缓存不是同义词。缓存面向「计算或请求的结果复用」，享元面向「对象实例的复用」，前者替换的是耗时操作，后者替换的是内存占用。两者常一起出现，但解决的问题不同。

### 6. 对象池

对象池（Object Pool）预先创建一批对象循环使用，减少频繁创建与销毁的开销。它与享元常被并列讨论，语义差别在共享的时机：

| 维度 | 享元 | 对象池 |
| --- | --- | --- |
| 共享方式 | 多个逻辑实体同时共享同一实例 | 实例在时间上被复用，任一时刻只归一个使用者 |
| 对象状态 | 内部状态不可变，外部状态外置 | 每次取出前重置，可携带临时状态 |
| 主要收益 | 减少重复数据的内存占用 | 减少创建与销毁的开销 |
| 典型对象 | 样式、图标、配置 | 数据库连接、WebGL 纹理、DOM 节点 |

一个最小实现：

```js
function ObjectPool(factory, size) {
  const free = [];

  for (let i = 0; i < size; i++) {
    free.push(factory());
  }

  return {
    acquire() {
      return free.pop() || factory();
    },
    release(obj) {
      // reset state before reuse
      obj.reset?.();
      free.push(obj);
    },
  };
}

const pool = ObjectPool(() => ({ reset() {} }), 4);
const item = pool.acquire();
pool.release(item);
```

- `acquire` 优先取出空闲对象，池空时按需扩容或阻塞，策略取决于资源成本。
- `release` 必须重置状态，遗漏会把上一个使用者的数据带给下一个。
- 池容量应与并发峰值匹配：过小导致频繁扩容，过大则长期占用内存却闲置。

对象池的典型风险是「归还遗漏」：使用者忘记 `release`，池内可用对象逐渐耗尽，表现为请求排队或超时。用 `try/finally` 包裹使用过程，或提供 `withPool` 这类作用域封装，可以把归还动作绑定到控制流上。

享元与对象池可以叠加：共享实例本身由池管理，外部状态通过参数传入。叠加的前提是两者解决的问题都真实存在，否则只是增加抽象层次。
