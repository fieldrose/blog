## 装饰器模式

装饰器在不改变原对象接口的前提下，为它叠加额外行为。与继承的区别在于叠加发生在运行时、按需组合，而不是在编译期枚举所有组合。JavaScript 中函数是一等对象，装饰最常见的形态是「接收函数、返回函数」。

### 1. 模拟传统面向对象的装饰器

咖啡店的定价是经典场景。基础饮料有 Espresso、HouseBlend，配料有牛奶、摩卡、奶泡，每加一种配料价格累加。用继承表达时，每种组合对应一个子类：

```ts
abstract class Beverage {
  abstract cost(): number;
}

class Espresso extends Beverage {
  cost() {
    return 2;
  }
}

class EspressoWithMilk extends Espresso {
  cost() {
    return super.cost() + 0.5;
  }
}

class EspressoWithMilkAndMocha extends EspressoWithMilk {
  cost() {
    return super.cost() + 0.7;
  }
}
```

两种饮料与三种配料的全组合是 2 × 2³ = 16 个类，新增一种配料会让类的数量翻倍。类名还在不断拉长，调用方必须提前知道自己要哪个子类，无法在运行时决定加什么。

装饰者的做法是让配料也成为一种饮料，内部持有一个被装饰的饮料：

```ts
class Milk extends Beverage {
  constructor(private inner: Beverage) {
    super();
  }

  cost() {
    return this.inner.cost() + 0.5;
  }
}

class Mocha extends Beverage {
  constructor(private inner: Beverage) {
    super();
  }

  cost() {
    return this.inner.cost() + 0.7;
  }
}

const coffee = new Mocha(new Milk(new Espresso())); // 3.2
```

类的数量从组合数降为「饮料数 + 配料数」。配料可以任意嵌套、任意顺序，`new Milk(new Mocha(...))` 与 `new Mocha(new Milk(...))` 在只做加法时结果相同，在需要顺序的场景（例如奶泡必须在最后）则由调用方控制包装顺序。

### 2. 装饰者也是包装器

装饰者的结构可以概括为一句话：与被装饰对象实现同一接口，内部持有被装饰对象，调用时转发并附加行为。

```ts
abstract class Beverage {
  abstract cost(): number;
}
```

`Milk` 继承 `Beverage`，构造时接收一个 `Beverage`，`cost()` 中先调用 `inner.cost()` 再加上自己的价格。这带来三个性质：

- 调用方只依赖 `Beverage` 接口，感知不到包装了几层。
- 每一层只处理自己的增量，不需要了解其他层的存在。
- 包装可以在运行时进行，取决于用户选择了哪些配料。

这个结构本质是「组合优于继承」的一个具体形态：继承把变体固定在类型层级上，包装把变体变成对象组合。所有装饰者都满足「透传」约束——最终一定会调用到被装饰对象，否则它就不是装饰者，而是代理或替代实现。

### 3. 回到 JavaScript

JavaScript 没有抽象类与接口约束，装饰退化为更简单的形式：函数接收函数，返回新函数。

```js
function withLog(fn) {
  return function (...args) {
    console.log(fn.name || "anonymous", args);
    return fn.apply(this, args);
  };
}

function sum(a, b) {
  return a + b;
}

const loggedSum = withLog(sum);
loggedSum(1, 2); // logs "sum [1, 2]", returns 3
```

几个细节决定了这个包装是否可用：

- `fn.apply(this, args)` 而不是 `fn(...args)` 直接调用，保证方法被装饰后 `this` 仍指向调用者。
- 原函数对象没有被修改，`sum` 仍然可以单独使用，包装产物是新的值。

### 4. 装饰函数与 AOP

AOP（面向切面编程）把「与主逻辑无关、但需要横切多个函数」的行为抽出来，在调用前后织入。JavaScript 中用三个高阶函数即可表达：

```js
function before(fn, hook) {
  return function (...args) {
    hook.apply(this, args);
    return fn.apply(this, args);
  };
}

function after(fn, hook) {
  return function (...args) {
    const result = fn.apply(this, args);
    hook.call(this, result);
    return result;
  };
}

function around(fn, hooks = {}) {
  return function (...args) {
    if (hooks.before && hooks.before.apply(this, args) === false) {
      return undefined;
    }
    const start = performance.now();
    try {
      return fn.apply(this, args);
    } finally {
      if (hooks.after) {
        hooks.after.call(this, performance.now() - start);
      }
    }
  };
}
```

三者的差异只在织入位置：

| 函数 | 执行顺序 | 能否中断主逻辑 | 典型用途 |
| --- | --- | --- | --- |
| `before` | hook → fn | 不能（返回值被忽略） | 参数校验、上报、设置标记 |
| `after` | fn → hook | 不能 | 结果记录、状态复位 |
| `around` | before → fn → after | 能（返回 `false`） | 防重复提交、耗时统计、错误包裹 |

`before` 与 `after` 内部的 `fn` 是闭包捕获的引用。这一点在处理宿主对象时很关键：

```js
const originalOnload = window.onload || function () {};

window.onload = before(originalOnload, function () {
  console.log("page ready");
});
```

先把 `window.onload` 保存到局部变量再装饰，而不是写成 `window.onload = before(window.onload, hook)` 反复执行。后者在脚本被重复加载（例如组件热更新）时会层层包裹，包装函数套住自己，最终形成递归调用。

### 5. AOP 应用实例

#### 5.1 日志与埋点

点击上报是典型的横切逻辑。业务函数只关心跳转，上报通过包装附加：

```js
function track(fn, event) {
  return function (...args) {
    navigator.sendBeacon?.("/collect", JSON.stringify({ event, ts: Date.now() }));
    return fn.apply(this, args);
  };
}

const goDetail = track(function (id) {
  location.href = `/detail/${id}`;
}, "click_detail");
```

#### 5.2 表单防重复提交

防重复提交需要在满足条件时跳过主逻辑，`before` 的返回值必须能被读取，因此用 `around`：

```js
let submitting = false;

const submit = around(
  function () {
    return fetch("/api/order", { method: "POST" });
  },
  {
    before() {
      if (submitting) {
        return false;
      }
      submitting = true;
      return true;
    },
    after() {
      submitting = false;
    },
  },
);
```

同步版本里 `finally` 在函数返回时立刻执行，标记能正确复位。异步请求则不同：`fetch` 返回 Promise 的瞬间主逻辑就「返回」了，`after` 会在请求完成前执行，标记提前复位，防重复提交失效。

异步场景需要等待 Promise 敲定后再复位：

```js
function aroundAsync(fn, hooks = {}) {
  return async function (...args) {
    if (hooks.before && hooks.before.apply(this, args) === false) {
      return undefined;
    }
    const start = performance.now();
    try {
      return await fn.apply(this, args);
    } finally {
      if (hooks.after) {
        hooks.after.call(this, performance.now() - start);
      }
    }
  };
}
```

`await` 让 `finally` 推迟到 Promise 敲定之后执行，`submitting` 的复位时机与请求生命周期对齐。这也是装饰异步函数时最容易写错的地方：包装函数的同步/异步性质必须与被包装函数一致，否则调用方 await 到的不是预期结果。

#### 5.3 执行时间统计

耗时统计只关心前后两个时间点，用 `around` 的 `after` 回调即可：

```js
const render = around(
  function (data) {
    return heavyTransform(data);
  },
  {
    after(elapsed) {
      if (elapsed > 16) {
        console.warn("frame budget exceeded", elapsed);
      }
    },
  },
);
```

`performance.now()` 的精度高于 `Date.now()`，在毫秒级测量中更可靠。阈值 16ms 对应 60fps 的单帧预算，超出说明这段逻辑可能造成掉帧。

### 6. 装饰者与代理的区别

两者的结构几乎一样：同一个接口、内部持有目标对象、转发调用。区别在目的与调用行为：

| 维度 | 装饰者 | 代理 |
| --- | --- | --- |
| 目的 | 增加职责 | 控制访问 |
| 是否调用目标 | 必然调用，且通常透传结果 | 可能不调用（缓存命中、权限拒绝、懒加载） |
| 层数 | 可多层叠加，顺序敏感 | 通常一层 |
| 接口 | 与被装饰对象一致 | 与目标对象一致 |
| 创建时机 | 调用方按需包装 | 常在访问入口处创建 |
| 典型例子 | 日志、埋点、防抖、耗时统计 | 图片懒加载、请求缓存、权限保护 |

判断依据是「目标方法的调用是否仍然发生」：装饰者把调用当作必然，只是在其前后附加行为；代理把调用当作可选项，代理自己就能给出结果。

一个容易混淆的例子是缓存。带缓存的请求函数会在命中时直接返回，不调用原方法，这是代理；如果包装函数每次都调用原方法、只是额外记录命中率，就是装饰者。

### 7. 现代语境

装饰器语法把这种包装提升为语言特性：

```ts
function logged(value: Function, context: ClassMethodDecoratorContext) {
  return function (this: unknown, ...args: unknown[]) {
    console.log(`call ${String(context.name)}`);
    return value.apply(this, args);
  };
}

class OrderService {
  @logged
  create() {
    // ...
  }
}
```

标准装饰器（TC39 Stage 3，TypeScript 5 起默认支持）的运行时语义仍然是「接收原方法、返回新方法」，只是由编译器负责替换，写法更贴近声明。它与高阶函数包装是同一机制的不同入口，理解后者才能判断装饰器叠加顺序、`this` 绑定与类型推导的行为。

同样的结构在框架里换了名字：

| 形态 | 被装饰对象 | 附加职责 |
| --- | --- | --- |
| 高阶组件 HOC | 组件 | 注入 props、权限校验、加载态 |
| Redux middleware | `dispatch` | 日志、异步、错误上报 |
| Koa middleware | 请求处理链 | 日志、鉴权、响应包装 |
| 装饰器语法 | 类、方法、字段 | 元数据、校验、缓存 |

这些形态都不是新的模式，而是包装器在不同调用约定下的具体写法。判断一段代码是不是装饰，看三点：是否保持原接口、是否必然调用原逻辑、是否可以在运行时叠加。
