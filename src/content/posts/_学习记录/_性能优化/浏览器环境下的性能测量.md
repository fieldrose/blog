## 一、测量基础：Performance API

### 1.1 时间原点与单调时钟

```ts
performance.now(); // 相对 timeOrigin 的毫秒数，带小数
performance.timeOrigin; // timeOrigin 对应的 Unix 时间戳
```

- `performance.now()` 基于单调时钟，不受系统时间调整影响，适合计算耗时。
- `Date.now()` 可能因系统校时发生跳变，不能用于区间测量。
- 页面级时间戳转换为绝对时间：`performance.timeOrigin + performance.now()`。
- 计时精度受安全策略限制：非跨域隔离环境下会被粗化到 100µs–1ms 量级，短耗时测量需要多次采样。

### 1.2 PerformanceEntry 与 PerformanceObserver

```ts
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // entry.entryType 决定可用字段
    console.log(entry.entryType, entry.startTime, entry.duration);
  }
});

observer.observe({ type: "resource", buffered: true });
```

- 所有性能数据都是 `PerformanceEntry` 的子类，公共字段为 `name`、`entryType`、`startTime`、`duration`。
- `buffered: true` 用于补采注册前产生的条目；注册过晚又未开 buffered 会丢失首屏数据。
- `PerformanceObserver.supportedEntryTypes` 可在运行时检测浏览器能力，作为降级依据。
- 一个 observer 可以监听多个类型，但回调内需要按 `entryType` 分支处理。

### 1.3 自定义阶段：mark 与 measure

```ts
performance.mark("feed:start");
await fetchFeed();
performance.mark("feed:end");
performance.measure("feed:fetch", "feed:start", "feed:end");

const [measure] = performance.getEntriesByName("feed:fetch");
console.log(measure.duration);
```

- 业务阶段耗时用 `mark`/`measure` 记录，比在代码里到处 `console.time` 更可控。
- 度量名称应带模块前缀，避免与第三方脚本冲突。
- 生产环境保留关键 measure，采样上报，而不是全部打开。

## 二、导航与资源时序

### 2.1 Navigation Timing

`PerformanceNavigationTiming` 把一次导航拆成若干时间点，是定位「慢在服务端还是慢在网络」的基础。

| 字段 | 含义 |
| ---- | ---- |
| `startTime` | 导航发起时间，作为页面内相对零点 |
| `redirectStart` / `redirectEnd` | 重定向起止 |
| `workerStart` | Service Worker 启动时间，未命中为 0 |
| `domainLookupStart` / `domainLookupEnd` | DNS 解析 |
| `connectStart` / `connectEnd` | TCP 建连 |
| `secureConnectionStart` | TLS 握手开始 |
| `requestStart` / `responseStart` | 请求发出、首字节到达 |
| `responseEnd` | 响应体接收完成 |
| `domInteractive` | DOM 解析完成 |
| `domContentLoadedEventEnd` | DOMContentLoaded 回调结束 |
| `loadEventEnd` | load 事件结束 |
| `activationStart` | 预渲染页面被激活的时间，未预渲染为 0 |

```ts
const [nav] = performance.getEntriesByType("navigation") as PerformanceNavigationTiming[];

const ttfb = nav.responseStart - nav.startTime;
const phases = {
  redirect: nav.redirectEnd - nav.redirectStart,
  dns: nav.domainLookupEnd - nav.domainLookupStart,
  tcp: nav.connectEnd - nav.connectStart,
  tls: nav.secureConnectionStart > 0 ? nav.connectEnd - nav.secureConnectionStart : 0,
  request: nav.responseStart - nav.requestStart,
  response: nav.responseEnd - nav.responseStart,
};
```

- TTFB 定义为 `responseStart - startTime`，包含重定向、DNS、建连与请求等待。
- `nextHopProtocol` 可区分 `h2`、`h3`，用于验证协议升级是否生效。
- 预渲染页面必须用 `activationStart` 修正时间原点，否则 LCP 会被算成负值或异常大。
- bfcache 恢复的页面不会产生完整导航时序，需要用 `pageshow` 的 `persisted` 判断。

### 2.2 Resource Timing

```ts
const slowest = performance
  .getEntriesByType("resource")
  .filter((entry) => entry.duration > 500)
  .sort((a, b) => b.duration - a.duration);
```

- `initiatorType` 标识资源由谁发起（`script`、`link`、`img`、`fetch`、`xmlhttprequest`），可用于绘制请求瀑布。
- `transferSize` 是线上传输字节数（含响应头），`encodedBodySize` 是压缩后体积，`decodedBodySize` 是解压后体积，三者结合能判断压缩与缓存是否生效。
- `transferSize` 为 0 通常意味着命中本地缓存，或跨域资源未授权。
- 跨域资源默认只暴露时间点、不暴露体积，需要响应头 `Timing-Allow-Origin` 才能拿到完整数据。
- 资源条目数量多时会占用内存，生产采集一般只上报聚合结果而非全量条目。

### 2.3 Server-Timing

```http
Server-Timing: db;dur=53, cache;desc="hit";dur=2
```

```ts
const [nav] = performance.getEntriesByType("navigation") as PerformanceNavigationTiming[];
console.log(nav.serverTiming);
```

- 服务端把内部阶段通过 `Server-Timing` 回传，浏览器解析为 `serverTiming` 数组。
- 这是打通前后端归因的最低成本方式，能区分「接口慢」与「网络慢」。
- 生产环境建议只暴露粗粒度阶段，避免泄露内部服务名与实现细节。

## 三、渲染与交互相关的 entry

### 3.1 Paint Timing 与 LCP

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    const lcp = entry as PerformanceEntry & { element?: Element; url?: string; size: number };
    // renderTime 优先，图片尚未解码时用 loadTime
    console.log(lcp.element, lcp.size, lcp.startTime);
  }
}).observe({ type: "largest-contentful-paint", buffered: true });
```

- `paint` 类型包含 `first-paint` 与 `first-contentful-paint` 两个条目，后者才是 FCP。
- LCP 条目持续更新，直到用户首次输入或页面隐藏；采集最终值需要在 `pagehide` 或首次输入时固化。
- `element` 字段能直接定位 LCP 元素，是排查时最有用的信息。
- `renderTime` 为 0 时说明是跨域图片且未授权，应回退到 `loadTime`。

### 3.2 Layout Instability

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as (PerformanceEntry & {
    value: number;
    hadRecentInput: boolean;
    sources: unknown[];
  })[]) {
    if (!entry.hadRecentInput) console.log(entry.value, entry.sources);
  }
}).observe({ type: "layout-shift", buffered: true });
```

- 单条 `value` 是一次偏移分数，CLS 需要按会话窗口聚合，不能简单求和。
- `hadRecentInput` 为真的条目应在计算 CLS 时排除。
- `sources` 指向发生偏移的节点，能直接定位「是谁把页面顶下去了」。

### 3.3 Long Tasks 与 LoAF

- `longtask` 条目表示超过 50ms 的主线程任务，字段较少，只能给出起止时间。
- `long-animation-frame`（LoAF）把单帧拆成脚本、样式与布局、渲染等阶段，能指出具体是哪个脚本造成长帧。
- 长任务观察器本身有开销，生产环境按采样开启。
- 这两类指标用于归因，不建议直接作为对外指标。

### 3.4 Event Timing 与 INP

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as (PerformanceEntry & {
    processingStart: number;
    processingEnd: number;
    interactionId?: number;
  })[]) {
    const inputDelay = entry.processingStart - entry.startTime;
    const processing = entry.processingEnd - entry.processingStart;
    const presentation = entry.startTime + entry.duration - entry.processingEnd;
    console.log({ inputDelay, processing, presentation });
  }
}).observe({ type: "event", buffered: true, durationThreshold: 16 });
```

- `durationThreshold` 最小为 16ms，低于阈值的交互不会产生条目。
- 只有带 `interactionId` 的条目属于离散交互，连续滚动等不算。
- INP 取交互延迟的高分位，通常直接使用 `web-vitals` 的计算结果，不建议自行实现分位数逻辑。

## 四、浏览器差异：Chromium、WebKit、Gecko

同一段采集代码在不同内核上拿到的数据并不等价。

| 能力 | Chromium | WebKit（Safari / iOS） | Gecko（Firefox） |
| ---- | -------- | ---------------------- | ---------------- |
| Paint Timing（FCP） | 支持 | 支持 | 支持 |
| LCP | 支持 | 支持 | 支持较晚 |
| CLS（Layout Instability） | 支持 | 支持 | 未实现 |
| Event Timing（INP） | 支持 | 未实现 | 未实现 |
| Long Tasks | 支持 | 未实现 | 未实现 |
| LoAF | 支持 | 未实现 | 未实现 |
| Resource Timing 体积字段 | 完整 | 跨域裁剪更严格 | 较完整 |

- 支持情况随版本变化，落地前以 MDN 与 caniuse 的当前表格为准，不长期依赖记忆。
- WebKit 缺少 Event Timing，INP 无法直接测量，只能用 FID 与自定义「事件到下一帧」的差值近似。
- iOS 上所有浏览器共用 WebKit 内核，iOS Chrome 的数据分布与 Safari 接近，不能按桌面 Chrome 的经验解读。
- Gecko 缺少布局偏移条目，CLS 需要靠 `ResizeObserver` 或 DOM 快照对比自建近似值。
- 跨内核比较指标绝对值意义不大，更有价值的是同内核同版本的纵向对比。

## 五、实验室工具与现场采集

### 5.1 实验室

- Lighthouse 给出分项得分与优化建议，适合 CI 卡点，但评分模型会随版本变化，跨版本对比要看分项而非总分。
- DevTools Performance 面板提供逐帧火焰图，适合定位长任务与强制同步布局。
- WebPageTest 支持多地区、多设备、真实网络录制，适合分析首屏影片条。
- 所有实验室结论都依赖 throttling 配置，配置不同则数字不可比。

### 5.2 现场

```ts
import { onCLS, onINP, onLCP } from "web-vitals/attribution";

onINP((metric) => {
  // attribution 给出输入延迟、处理时间、呈现延迟的拆分与目标元素
  navigator.sendBeacon("/api/rum", JSON.stringify(metric));
});
```

- attribution 构建会附带归因信息，代价是体积略大，适合按比例采样加载。
- 上报要带维度：设备档位、网络类型、内核版本、应用版本、页面类型、冷热启动。
- 单页应用按路由生成虚拟页面标识，并在路由切换时重新初始化指标。
- 页面卸载用 `pagehide` 而不是 `unload`，后者在移动端与 bfcache 场景不可靠。

## 六、测量误差与常见陷阱

- **缓存状态不同**：首次访问与二次访问的 LCP 可能相差数倍，报表必须区分。
- **采样偏差**：只统计能跑监控脚本的设备，会漏掉老设备与低端机，长尾被系统性低估。
- **平均值误导**：性能分布长尾明显，P75 比均值更能代表多数用户的体验。
- **时间原点错位**：预渲染、bfcache、iframe 内页面的时间基准都可能不同，混算会产生假数据。
- **后台标签页**：页面不可见时 `requestAnimationFrame` 暂停，相关耗时不能代表用户可见体验。
- **监控自身开销**：观察器与上报都会占用主线程，采样与异步上报是必要约束。
- **开发环境失真**：未压缩资源、sourcemap、开发服务器与生产差异巨大，优化验证必须在生产构建上进行。
