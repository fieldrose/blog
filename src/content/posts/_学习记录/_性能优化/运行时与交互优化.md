加载完成只解决了「看得见」，交互流畅才决定「好不好用」。运行时的所有优化最终都指向一个资源：主线程。本文按「长任务 → 输入响应 → DOM 与渲染 → 计算与内存」组织。

## 一、主线程是唯一瓶颈

主线程同时承担 JS 执行、样式计算、布局、绘制与合成调度。任何一段占用过久，输入事件就无法被及时处理，表现为点击无反应或延迟响应。

- 超过 50ms 的任务被视为长任务，长任务期间浏览器无法响应输入。
- INP 的问题通常出在「输入延迟」一段，而不是事件处理函数本身慢。
- 长任务既可能来自业务代码，也可能来自框架更新、第三方脚本、样式计算或布局。
- LoAF 能把单个长帧拆成脚本、样式与布局、渲染等阶段，是定位长任务的首选工具。

### 1.1 任务拆分

```ts
async function processInChunks<T>(items: T[], handle: (item: T) => void) {
  for (let i = 0; i < items.length; i++) {
    handle(items[i]);
    if (i % 50 === 49) {
      // 让出主线程，给输入与渲染机会
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
  }
}
```

- 拆分的目的是让主线程在任务之间有机会处理输入与绘制，而不是单纯追求更短的函数。
- 单个分片过小会引入大量调度开销，分片大小应按实际耗时测量后确定。
- 拆分过程中状态可能被用户操作改变，需要处理中断、取消与幂等。
- 拆分后总耗时可能上升，优化目标应是「响应及时」而不是「总时长最短」。

### 1.2 优先级调度

- 高优先任务（用户输入、动画）应立即执行，低优先任务（预计算、日志）可延后。
- `requestIdleCallback` 适合真正可延后的工作，但浏览器空闲时间不保证，不能承载关键逻辑。
- Chromium 提供 `scheduler.postTask` 与 `isInputPending`，可感知输入并主动让出，但需要能力检测与回退。
- 框架层的并发渲染与批处理本质上也是优先级调度，理解其成本比盲目开启更重要。

## 二、事件处理与输入响应

### 2.1 减少输入延迟

- 避免在 `pointerdown`、`touchstart` 中执行同步重计算，先反馈再计算。
- 滚动与触摸监听使用 `{ passive: true }`，避免浏览器等待监听器执行而阻塞滚动。
- 事件委托减少监听器数量，但委托到根节点会让所有事件都经过同一回调，需避免在其中做重活。
- 高频事件（滚动、鼠标移动）要限制处理频率，低频事件（点击、提交）不应无谓延迟。

### 2.2 防抖与节流

```ts
function debounce<T extends (...args: never[]) => void>(fn: T, wait = 200) {
  let timer: ReturnType<typeof setTimeout> | undefined;
  return (...args: Parameters<T>) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), wait);
  };
}

function throttle<T extends (...args: never[]) => void>(fn: T, interval = 100) {
  let last = 0;
  return (...args: Parameters<T>) => {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn(...args);
    }
  };
}
```

- 防抖适合输入搜索、窗口尺寸变化等「只关心最终结果」的场景。
- 节流适合滚动进度、拖拽位置等「需要持续反馈」的场景。
- 点击提交类操作不应防抖或节流，用户需要即时反馈，重复提交应在业务层幂等处理。
- 节流间隔过大会让交互显得迟滞，间隔应按帧率与业务容忍度确定。

### 2.3 先反馈后计算

- 点击后先切换按钮状态或展示加载态，再执行耗时逻辑，可显著降低感知延迟。
- 同步计算期间界面完全冻结，任何视觉反馈都无法呈现。
- 反馈元素本身要轻量，避免为了显示 loading 触发大规模重渲染。

## 三、DOM 与渲染开销

### 3.1 批量更新与读写分离

```js
// 反例：读写交替，每次写后读都会触发强制同步布局
for (const el of items) {
  const height = el.offsetHeight;
  el.style.height = `${height + 10}px`;
}

// 正例：先集中读取，再集中写入
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => {
  el.style.height = `${heights[i] + 10}px`;
});
```

- 强制同步布局是运行时卡顿的常见来源，读取 `offsetHeight`、`getBoundingClientRect` 等属性前应确保没有待处理的样式写入。
- 批量插入使用 `DocumentFragment`，减少 DOM 变更次数与重排次数。
- 多次状态变更合并到一次渲染，避免同一帧内反复更新。
- 虚拟 DOM 框架下同样存在强制同步布局，只是隐藏在生命周期或测量逻辑中。

### 3.2 长列表

- 虚拟滚动只渲染视口内节点，是长列表最直接的手段，但高度不固定的列表实现复杂。
- `content-visibility: auto` 配合 `contain-intrinsic-size` 可跳过离屏渲染，适合结构稳定的长页面。
- `IntersectionObserver` 用于懒加载与曝光统计，比监听滚动事件更高效。
- 分页或无限滚动要把渲染成本计入交互延迟，追加大量节点会造成长任务。

### 3.3 动画与合成

- 只对 `transform` 与 `opacity` 做动画，避免触发布局与重绘。
- `will-change` 提前提升合成层，但长期保留会增加内存占用。
- 动画期间避免读取布局属性，强制同步布局会打断合成节奏。
- 低端设备上减少同时运行的动画数量，合成层过多同样会掉帧。

## 四、计算与内存

### 4.1 Web Worker

```ts
// main.ts
const worker = new Worker(new URL("./worker.ts", import.meta.url), { type: "module" });
worker.postMessage({ type: "parse", payload: largeText });
worker.onmessage = (event) => render(event.data);

// worker.ts
self.onmessage = (event) => {
  const result = parse(event.data.payload);
  self.postMessage(result);
};
```

- 解析、加密、压缩、图像处理、大数据计算适合迁移到 Worker，避免占用主线程。
- `postMessage` 的结构化克隆有成本，大对象应使用 `Transferable` 转移所有权。
- Worker 适合粗粒度任务，过于频繁的小消息往返会抵消收益。
- OffscreenCanvas 可把绘制也移出主线程，但兼容性与调试成本需要评估。

### 4.2 内存与回收

- 未移除的事件监听、未清理的定时器、闭包持有的大对象是常见泄漏源。
- 全局缓存要有上限与淘汰策略，否则页面停留越久内存越高。
- `WeakMap`、`WeakRef` 适合以 DOM 节点或对象为键的关联数据，避免阻止回收。
- Chromium 提供 `performance.memory` 与 `measureUserAgentSpecificMemory`，后者需要跨域隔离，其他内核支持有限。
- 内存问题在低端设备与长时停留场景更明显，应结合崩溃率与页面停留时长一起观察。

### 4.3 框架运行时成本

- 响应式系统的依赖收集与更新调度有固定开销，深层嵌套与超大数据源会放大成本。
- 虚拟 DOM 的 diff 与补丁阶段占用主线程，列表 key 不稳定会导致不必要的重建。
- 组件级缓存（`memo`、`computed`、`shallowRef`）应基于测量结果添加，过早优化会增加复杂度。
- 状态更新粒度越粗，单次渲染范围越大，交互延迟越难控制。

## 五、验证与误区

- **用微基准代替真实测量**：循环、字符串拼接等微优化对 INP 的影响通常可以忽略。
- **过早 memo**：缓存比较本身有成本，且可能掩盖真正的长任务。
- **Worker 滥用**：消息序列化与线程启动成本可能高于计算本身。
- **只优化回调耗时**：INP 的大头常在输入延迟，减少长任务比优化回调更有效。
- **忽略第三方脚本**：埋点、客服、广告脚本在主线程上的执行同样计入交互延迟。

验证以现场 INP 归因为主，实验室 Performance 面板为辅，按交互类型分桶（点击、输入、滚动），确认优化命中的是真实长尾。
