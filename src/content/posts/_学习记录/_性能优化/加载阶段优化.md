## Table of contents

> 本文属于 Mimas 个人技术博客（Astro 7 + TypeScript + Tailwind CSS 4，中英双语站点）的博客文章，项目语境见 `.trae/rules/doc-gen/00-context.md`。

加载阶段的指标是 TTFB、FCP、LCP，优化手段最终都落在三个问题上：下载多少、什么时候下载、能不能不下载。本文按这个顺序组织，每一类手段都对应可验证的指标变化。

## 一、先看请求瀑布

在改任何配置之前，先把首屏请求按时间顺序画出来。

```ts
const entries = performance.getEntriesByType("resource") as PerformanceResourceTiming[];

const waterfall = entries
  .filter((entry) => entry.startTime < 3000)
  .map((entry) => ({
    name: entry.name,
    type: entry.initiatorType,
    start: Math.round(entry.startTime),
    duration: Math.round(entry.duration),
    size: entry.transferSize,
  }));
```

- 瀑布图要回答三个问题：首屏阻塞资源有几个、关键资源是否存在串行依赖、哪些资源在首屏根本用不到。
- HTML → CSS → JS → 首屏接口 → 图片是最常见的串行链，链越长，LCP 越晚。
- 同域并发连接数有限，大量小请求会排队；HTTP/2 多路复用能缓解，但不能消除带宽竞争。
- 首屏接口的串行等待属于「数据链路」，与资源加载是两条并行的关键路径，需要分别度量。

## 二、减少下载体积

### 2.1 代码分割

```ts
const Detail = () => import("@/views/Detail.vue");
```

```ts
// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          "vendor-framework": ["vue", "vue-router", "pinia"],
          "vendor-utils": ["axios", "dayjs"],
        },
      },
    },
  },
});
```

- 路由级分割是收益最确定的一层，保证首屏只加载当前页代码。
- 弹窗、图表、富文本编辑器等重组件延迟到交互时再加载，避免进入页面就付出成本。
- 过度分割会带来更多请求与调度开销，小 chunk 合并比拆得更细更划算。
- 分包的目标之一是长期缓存：框架与业务代码分离后，框架升级不会让业务 chunk 全部失效。

### 2.2 Tree shaking 与产物压缩

- Tree shaking 依赖 ESM 的静态结构，CommonJS 模块和动态属性访问会让未使用代码无法被消除。
- `package.json` 的 `sideEffects` 声明能让打包器安全地删除无副作用模块，声明缺失会保留整包。
- 组件库优先按需引入，避免整库注册；工具库优先选择 ESM 版本。
- 压缩层面，JavaScript 用 esbuild 或 terser，开启 `drop_console` 需评估线上排障成本。
- 文本资源优先 Brotli，回退 gzip；压缩率与资源类型相关，图片、视频不要再做文本压缩。

### 2.3 依赖治理

- 重复依赖是体积膨胀的常见来源，同一库的多个版本会被打包成多份。
- 用产物分析工具查看 chunk 构成，优先处理占比最大的依赖，而不是逐个微调。
- 替换重型依赖（如用 `dayjs` 替代 `moment`）的收益通常高于代码层微优化。
- 引入新依赖前评估体积与替代方案，体积成本应进入评审，而不是等构建报警。

### 2.4 图片与字体

```html
<img
  src="hero-800.webp"
  srcset="hero-400.webp 400w, hero-800.webp 800w, hero-1600.webp 1600w"
  sizes="(max-width: 600px) 100vw, 800px"
  width="800"
  height="450"
  fetchpriority="high"
  alt="首屏主图"
/>
```

- 图片优先 AVIF、WebP，按展示尺寸生成多档，避免用大图缩放展示。
- 首屏图片不要 `loading="lazy"`，否则会推迟 LCP；非首屏图片应懒加载。
- 宽高或 `aspect-ratio` 必须声明，否则加载完成后的重排会同时恶化 LCP 与 CLS。
- 字体做子集化，只保留实际使用的字符范围；`font-display: swap` 保证文本先可见。
- 字体文件用 `preload` 提前加载，但要限制数量，避免与首屏图片争抢带宽。

## 三、调整下载时机

### 3.1 资源提示

```html
<link rel="preconnect" href="https://img.example.com" crossorigin />
<link rel="dns-prefetch" href="https://api.example.com" />
<link rel="preload" href="/fonts/main.woff2" as="font" type="font/woff2" crossorigin />
<link rel="prefetch" href="/assets/next-page.js" />
```

- `preconnect` 提前完成 DNS、TCP、TLS，适合确定会用的第三方域；数量过多会适得其反。
- `dns-prefetch` 成本更低，作为 `preconnect` 的兼容兜底。
- `preload` 只用于当前页面确定需要且发现较晚的关键资源，滥用会挤占带宽并触发未使用警告。
- `prefetch` 面向下一次导航，优先级低，不应与首屏资源争夺。
- 预渲染可用 Speculation Rules，但要注意统计与副作用，不是所有页面都适合。

### 3.2 优先级控制

- `fetchpriority="high"` 提升 LCP 图片的下载优先级；`fetchpriority="low"` 可用于非关键图片。
- 同步 `<script>` 阻塞解析，`defer` 延迟到解析完成后按序执行，`async` 下载完立即执行，`type="module"` 默认延迟。
- CSS 默认阻塞渲染，首屏关键样式应内联或优先加载，非关键样式可异步化。
- 优先级是相对的，当所有资源都标 high 时等于没有优先级。

### 3.3 首屏数据

- SSR 直出能让 HTML 到达时即带内容，消除客户端首屏请求瀑布。
- BFF 聚合把多个接口合并为一次往返，减少弱网下的 RTT 放大。
- 多接口并行请求优于串行依赖，但要注意浏览器并发限制与服务端压力。
- 预取下一屏数据或 hover 预取详情，可把等待转移到用户思考时间，但要控制失败与浪费。

## 四、缓存与传输

### 4.1 HTTP 缓存

| 资源 | 建议策略 |
| ---- | -------- |
| 带内容哈希的 JS / CSS / 图片 | `public, max-age=31536000, immutable` |
| HTML | `no-cache` + ETag，每次协商 |
| 接口数据 | 按变化频率设置短 TTL，或 `stale-while-revalidate` |
| 字体 | 长缓存 + 内容哈希文件名 |

- 文件名带哈希是长缓存的必要条件，否则发版后用户会拿到旧资源。
- HTML 不缓存，保证用户总能拿到指向最新哈希资源的入口。
- `stale-while-revalidate` 让用户先拿到旧数据，同时后台刷新，适合变化不频繁的列表与配置。
- 缓存策略要同时考虑 CDN 与浏览器两层，只配一层会出现「回源了但用户仍拿旧文件」。

### 4.2 CDN 与协议

- HTTP/2 多路复用消除了域分片的主要动机，静态资源域名收敛更利于连接复用。
- HTTP/3 基于 QUIC，弱网与移动网络下握手与丢包恢复更优，可作为 CDN 侧优化项。
- 静态资源使用独立域名时，注意 Cookie 与证书成本，避免不必要的请求头膨胀。
- 边缘缓存命中率是 CDN 的核心指标，命中率低时先查缓存键是否包含随机参数。

### 4.3 Service Worker 与离线包

- Service Worker 可预缓存应用壳与静态资源，首屏不再依赖网络。
- 更新策略要处理「新版本等待激活」的问题，`skipWaiting` 会让新旧资源混用，需配合刷新提示。
- Hybrid 场景的离线包本质是同一思路，容器拦截请求并返回本地资源，需记录命中率与回退原因。
- 缓存不是越多越好，预缓存列表过大会推迟安装完成时间，反而延长首次可用时间。

## 五、验证与常见误区

- **只看构建体积**：构建产物未经压缩，与线上传输体积差异明显，预算应基于压缩后体积。
- **只看首次访问**：二次访问命中缓存后，瓶颈可能转移到接口或主线程，优化方向完全不同。
- **把 LCP 元素懒加载**：懒加载只适用于首屏之外，LCP 图片必须尽早发现与加载。
- **过度分包**：请求数增加带来的调度与解析成本可能抵消体积收益。
- **全站 preload**：关键资源之外的 preload 会降低真正关键资源的优先级。
- **忽略第三方脚本**：统计、客服、广告脚本常是体积与长任务的主要来源，应纳入预算。

验证方式固定为三条：构建产物体积对比、请求瀑布对比、现场 LCP 与 TTFB 分桶对比。三者同时改善，才能确认优化真实生效。
