LCP、INP、CLS 达标只说明页面没有明显短板，用户是否觉得「顺」还取决于等待是否被解释、反馈是否及时、内容是否渐进出现。本文讨论感知层的优化，以及如何避免把体验优化做成指标美化。

## 一、感知性能

用户感知的不是毫秒数，而是「操作后有没有回应」。同样的 800ms 等待，有进度提示与无任何反馈的体验差距远大于数字本身。

| 等待时长 | 用户感受 | 应对策略 |
| -------- | -------- | -------- |
| < 100ms | 即时 | 无需提示，直接呈现结果 |
| 100ms – 300ms | 轻微延迟 | 按钮态变化、局部 loading |
| 300ms – 1s | 明显等待 | 骨架屏、进度指示、内容分块出现 |
| > 1s | 注意力转移 | 说明进度、允许离开、提供可中断操作 |

- 100ms 与 1s 是常用的经验阈值，来源于对即时感与注意力保持的观察，不是标准规定。
- 感知优化的目标是让等待变得可预期，而不是掩盖等待。
- 无反馈的等待会被用户重复触发，造成重复请求与更差的实际性能。

### 1.1 感知优化不等于指标美化

- 通过延迟上报、隐藏元素、把内容移出视口来改善指标，属于数据修饰，真实体验没有变化。
- 感知优化的前提是真实瓶颈已定位，只是把剩余等待表达清楚。
- 指标与感知出现冲突时，先修指标，再调整呈现方式。

## 二、加载体验

### 2.1 骨架屏与占位

- 骨架屏的结构应与最终内容一致，尺寸差异过大会在替换时产生布局偏移。
- 首屏骨架只覆盖首屏区域，全页骨架会让用户误以为整页都在加载。
- 骨架屏动画要轻量，避免用高成本动画进一步占用主线程。
- 骨架显示时长应与真实加载时间匹配，过短会闪烁，过长会被识别为假内容。

### 2.2 渐进式内容

- 流式渲染先输出页面框架与已就绪数据，让用户尽早看到结构。
- 图片使用 LQIP、BlurHash 或低分辨率占位，先给轮廓再替换为高清图。
- 列表分块加载，优先渲染首屏可见项，其余随滚动补充。
- 渐进呈现的顺序应与用户关注点一致，把重要信息放在前面的分块。

### 2.3 预取与预测

- 在 hover、进入视口或路由预判时预取下一页资源，把等待转移到用户思考时间。
- 预取要设上限并允许取消，失败与浪费的带宽同样有成本。
- Speculation Rules 可预渲染整页，但要评估内存、统计重复与副作用。
- 移动网络下预取应更保守，避免与当前页面关键资源争夺带宽。

## 三、交互体验

### 3.1 乐观更新

```ts
async function toggleLike(id: string) {
  const previous = store.likes.has(id);
  store.likes.set(id, !previous); // 先更新界面

  try {
    await api.toggleLike(id);
  } catch {
    store.likes.set(id, previous); // 失败回滚
    toast("操作失败，请重试");
  }
}
```

- 乐观更新适合成功率高、回滚成本低的操作，如点赞、收藏、开关。
- 支付、删除、权限变更等不可逆操作不适合乐观更新，应以服务端确认为准。
- 回滚时必须给出明确提示，否则用户会认为操作丢失。
- 乐观更新减少的是感知等待，不会降低接口真实耗时。

### 3.2 过渡与动效

- 动效用于解释状态变化，例如面板展开、列表插入、页面切换。
- 常见时长在 150ms–300ms，过长会延迟信息获取，过短会显得突兀。
- 动效只使用 `transform` 与 `opacity`，避免触发布局与重绘。
- 响应 `prefers-reduced-motion`，为对动效敏感的用户提供无动画版本。

### 3.3 反馈闭环

- 提交类按钮在请求期间禁用并展示 loading，防止重复提交。
- 长任务展示进度或阶段提示，让用户知道系统仍在工作。
- 失败要提供重试入口，而不是只弹一句错误。
- 反馈元素出现与消失要一致，避免状态闪烁造成不确定感。

## 四、弱网与低端设备

### 4.1 自适应加载

```ts
const connection = (navigator as Navigator & {
  connection?: { effectiveType?: string; saveData?: boolean };
}).connection;

const lowEnd = navigator.hardwareConcurrency !== undefined && navigator.hardwareConcurrency <= 2;
const saveData = connection?.saveData === true;
const slowNetwork = connection?.effectiveType === "2g" || connection?.effectiveType === "slow-2g";

const imageQuality = saveData || slowNetwork ? "low" : lowEnd ? "medium" : "high";
```

- Network Information API 在 Chromium 可用，Safari 不支持，必须提供默认值。
- `deviceMemory`、`hardwareConcurrency` 也只能作为启发式信号，不能当作精确档位。
- 降级对象包括图片清晰度、视频自动播放、动画数量、预取范围与第三方脚本。
- 自适应加载的目标是保住核心功能，而不是让低端用户看到残缺页面。

### 4.2 弱网策略

- 设置合理的请求超时与重试次数，指数退避，避免弱网下请求堆积。
- 合并并发请求，减少同域连接竞争；首屏接口优先，非关键请求延后。
- Hybrid 场景优先使用离线包与本地缓存，弱网时直接读本地资源。
- 弱网下的加载态要更明确，避免用户反复刷新造成雪崩。

### 4.3 分桶与灰度

- 按设备档位、网络类型、地区、应用版本分桶看指标，避免平均值掩盖长尾。
- 低端机单独设定预算与验收标准，不用高端机数据推断整体。
- 优化上线先灰度，对比实验组与对照组的指标分布，而不只是看单点数值。
- 灰度期间同时观察业务指标，避免为了性能牺牲转化。

## 五、性能预算与持续守护

### 5.1 预算设定

| 预算类型 | 示例 | 说明 |
| -------- | ---- | ---- |
| 体积预算 | 首屏 JS 压缩后不超过 170KB | 经验阈值，需按业务调整 |
| 请求预算 | 首屏请求数不超过 30 个 | 控制瀑布与连接竞争 |
| 指标预算 | P75 LCP ≤ 2.5s、INP ≤ 200ms | 与 Core Web Vitals 阈值对齐 |
| 资源预算 | 首屏图片总字节不超过 500KB | 按设备档位分级 |

- 预算是团队共识，不是行业标准，数值应依据现有基线逐步收紧。
- 预算要能被自动检查，否则只会停留在文档里。
- 预算超限时应有明确的处理流程，而不是长期挂着的警告。

### 5.2 守护机制

- CI 中运行 Lighthouse CI 或等价工具，对关键页面做体积与指标卡点。
- 构建阶段检查 bundle 体积，超出阈值直接失败或要求说明。
- 线上 RUM 看板按页面、设备、版本分桶，设置 P75 回归告警。
- 发版后对比新旧版本的指标分布，定位回退引入的版本与改动。
- 定期清理失效的优化项，避免历史配置与新架构冲突。

### 5.3 协作方式

- 性能预算进入需求评审与技术方案评审，而不是上线前临时补测。
- 设计阶段考虑加载态、空态、错误态，减少实现阶段的返工。
- 第三方脚本引入需评估体积与主线程成本，并纳入统一预算。
- 性能数据定期回流到产品与设计，作为体验决策的依据。

## 六、体验优化的边界

- 先修真实瓶颈，再做感知层优化；顺序反了会掩盖问题。
- 骨架屏、动画、预取本身都有成本，低端设备上要做减法。
- 体验优化需要灰度或 A/B 验证，主观判断容易高估效果。
- 任何优化都不应以牺牲可访问性为代价，动效、对比度、键盘操作都要保留。
- 指标是底线，体验是目标，两者冲突时以真实用户任务完成为准。
