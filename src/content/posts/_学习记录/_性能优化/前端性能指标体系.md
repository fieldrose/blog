性能优化的第一步不是改代码，而是把「快」拆成可测量、可归因、可回归的指标。没有统一的度量口径，任何优化都无法证明有效，也无法在发版后防止回退。

## 一、指标的四条度量线

用户访问页面的过程可以切分为若干阶段，每个阶段对应一类指标。理解阶段划分比记住指标名字更重要，因为指标只是阶段的可观测代理。

```mermaid
flowchart LR
    A["导航发起"] --> B["首字节 TTFB"]
    B --> C["首次绘制 FCP"]
    C --> D["最大内容 LCP"]
    D --> E["可交互"]
    E --> F["交互响应 INP"]
    D --> G["布局稳定 CLS"]
```

| 度量线 | 代表指标 | 回答的问题 |
| ------ | -------- | ---------- |
| 加载速度 | TTFB、FCP、LCP | 内容什么时候可见 |
| 交互响应 | INP，历史上为 FID | 操作后多久有反馈 |
| 视觉稳定 | CLS | 内容会不会突然跳动 |
| 流畅度与主线程 | 长任务、TBT、LoAF、掉帧 | 主线程是否被长时间占用 |

- 加载类指标描述「等待」的结束时间点，交互类指标描述「响应」的延迟，二者不可互相替代。
- 视觉稳定不体现在时间轴上，但直接影响用户对「卡」和「乱」的判断。
- 流畅度指标多为诊断指标，用来解释 LCP 或 INP 为什么差，而不是最终结论。
- 资源成本类指标（传输体积、请求数）不面向用户，但决定加载类指标的上限。

### 1.1 实验室指标与现场指标

同一套指标有两种采集环境，分工不同。

| 类型 | 采集方式 | 优势 | 局限 |
| ---- | -------- | ---- | ---- |
| 实验室 | Lighthouse、DevTools Performance、WebPageTest | 可复现、可逐帧归因、可做 CI 卡点 | 样本单一，不代表真实用户分布 |
| 现场 | RUM，`web-vitals` 上报真实用户 | 反映设备、网络、地区、版本的分布 | 无法复现现场，归因依赖埋点设计 |

- 实验室指标用于定位与验证，现场指标用于判断优先级和回归。
- 现场数据看分位数而不是平均值，常用 P75：平均值会被少数极快或极慢的样本拉平，掩盖长尾。
- 实验室环境必须固定 throttling 配置（如 CPU 4 倍降速、Slow 4G），否则前后数据不可比。
- 两套数据出现分歧时，以现场为准判断用户影响，以实验室为准做技术归因。

## 二、Core Web Vitals

Core Web Vitals 是 Google 选定的三个用户中心指标，覆盖加载、交互、视觉稳定三个方面。2024 年 3 月起，INP 正式取代 FID。

### 2.1 LCP：最大内容绘制

LCP 记录视口内最大内容元素完成渲染的时间点。候选元素包括 `<img>`、`<image>`（SVG 内）、`<video>` 的封面图、带 `url()` 背景图的元素，以及包含文本的块级元素。

| 评级 | 阈值 |
| ---- | ---- |
| 良好 | ≤ 2.5s |
| 需要改进 | 2.5s – 4.0s |
| 差 | > 4.0s |

LCP 的可优化之处在于它可被拆成四段：

1. **TTFB**：服务器返回第一个字节前的时间；
2. **资源加载延迟**：HTML 到达后到开始加载 LCP 资源之间的时间，常见于资源发现晚、被其他请求排队；
3. **资源加载时长**：图片或字体的下载耗时；
4. **元素渲染延迟**：资源就绪到元素真正绘制之间的时间，常见于主线程被 JS 占用。

- LCP 在用户首次交互后停止更新，最终值只统计到首次输入前。
- 元素是文本时，瓶颈通常来自字体加载或阻塞渲染的 JS，而不是网络。
- 元素是图片时，`fetchpriority="high"`、`preload`、避免懒加载和避免用 CSS 背景图承载都直接影响该指标。
- 图片缺少固有尺寸时，加载完成后会触发重排，LCP 变差的同时 CLS 也会被拖累。

### 2.2 INP：交互到下一次绘制

INP 统计页面生命周期内所有交互的延迟，取约 98 分位作为代表值。一次交互的延迟由三段组成：

- **输入延迟**：从用户操作到事件回调开始执行，长任务占用主线程是主因；
- **处理时间**：事件回调及其触发的同步逻辑耗时；
- **呈现延迟**：处理完成到浏览器绘制出下一帧的时间，受样式计算、布局和合成影响。

| 评级 | 阈值 |
| ---- | ---- |
| 良好 | ≤ 200ms |
| 需要改进 | 200ms – 500ms |
| 差 | > 500ms |

- INP 与 FID 的关键差异：FID 只测首次输入的「输入延迟」一段，INP 覆盖全部交互与完整三段。
- 优化 INP 不是让回调跑得更快，而是减少主线程上的长任务，让输入有机会被及时处理。
- 键盘输入、点击、拖拽都会被计入，输入框的逐字响应往往是最敏感的场景。

### 2.3 CLS：累积布局偏移

CLS 衡量页面生命周期内非预期布局偏移的严重程度。单次偏移分数由「影响区域占比」与「移动距离占比」相乘得到，最终值取最大会话窗口（窗口间隔小于 1s，单个窗口最长 5s）内的累计值。

| 评级 | 阈值 |
| ---- | ---- |
| 良好 | ≤ 0.1 |
| 需要改进 | 0.1 – 0.25 |
| 差 | > 0.25 |

常见诱因：

- 图片、视频、iframe 未声明宽高或 `aspect-ratio`；
- 字体加载导致文本行高变化，回退字体与目标字体度量差异越大越明显；
- 首屏之后动态插入横幅、广告、提示条，把下方内容整体推移；
- 用 `top`、`left`、`height` 做动画，触发布局而不是仅合成。

- 用户输入后 500ms 内的偏移会被标记 `hadRecentInput` 并排除，因此「点击后展开」不算 CLS。
- 用 `transform` 做动画不会产生布局偏移，但会带来内容模糊与合成层开销，需要权衡。

## 三、辅助与诊断指标

Core Web Vitals 回答「用户感受如何」，辅助指标回答「为什么会这样」。

| 指标 | 含义 | 参考阈值 | 用途 |
| ---- | ---- | -------- | ---- |
| TTFB | 首字节时间 | ≤ 800ms | 区分服务端与前端问题 |
| FCP | 首次内容绘制 | ≤ 1.8s | 白屏结束的标志 |
| TBT | 主线程阻塞总时长 | ≤ 200ms（实验室） | 解释 INP 差的原因 |
| TTI | 可交互时间 | 仅作参考 | Lighthouse 10 起不再参与评分 |
| Speed Index | 内容可见的平均速度 | ≤ 3.4s（实验室） | 衡量渐进呈现的整体观感 |
| 长任务 | 超过 50ms 的主线程任务 | 越少越好 | 定位卡顿来源 |
| LoAF | 长动画帧 | 观测值 | 拆解单帧内的脚本、样式、布局耗时 |

- TTFB 高时，前端优化空间有限，应先查服务端、CDN 与网络链路。
- FCP 与 LCP 的差值反映「首屏主要内容何时出现」，差值过大说明关键资源发现或加载过晚。
- TBT 是实验室指标，与现场 INP 相关但不等价：主线程空闲不代表交互路径短。
- 长任务与 LoAF 是归因工具，不适合作为对外汇报的结论指标。
- TTI 定义复杂且对长任务敏感，Lighthouse 已移除其评分权重，阅读报告时不必围绕它做优化。

## 四、采集：从 Performance API 到 web-vitals

浏览器通过 Performance Timeline 暴露观测数据，核心接口是 `PerformanceObserver`。

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.entryType, entry.startTime, entry.duration);
  }
}).observe({
  type: "largest-contentful-paint",
  buffered: true, // 补采 observer 注册之前已经产生的条目
});
```

- `buffered: true` 保证注册较晚时仍能拿到早期条目，否则会漏掉首屏数据。
- 不同 entry 类型提供不同字段，例如 `layout-shift` 的 `value` 与 `sources`、`event` 的 `processingStart`，需要分别解析。
- 自建采集前先评估 `web-vitals`：它已处理了 LCP 停止时机、CLS 会话窗口、INP 分位数等细节。

```ts
import { onCLS, onINP, onLCP } from "web-vitals";

function report(metric: { name: string; value: number; rating: string; id: string }) {
  const body = JSON.stringify(metric);
  navigator.sendBeacon("/api/rum", body);
}

onLCP(report);
onINP(report);
onCLS(report);
```

- 上报使用 `sendBeacon` 或 `fetch` 的 `keepalive`，避免页面卸载时丢数据。
- 单页应用需要在路由切换时重置并生成新的虚拟页面标识，否则多个页面的指标会混在一起。
- 上报字段至少包含指标名、值、评级、页面标识、设备与网络分桶、应用版本，缺少维度就无法定位。
- 采样率按流量规模调整，但低端机与弱网样本不应被优先丢弃，它们恰恰是长尾来源。

## 五、指标之间的关系与取舍

指标之间会互相拉扯，优化一项常常以另一项为代价：

- 为降低 LCP 而内联关键 CSS，会增大 HTML 体积、拖慢 TTFB 与缓存复用；
- 为降低 INP 而拆分任务，会增加调度与状态同步成本，总耗时可能上升；
- 为减小首屏体积而全面懒加载，若把 LCP 元素也纳入懒加载，LCP 反而变差；
- 为消除 CLS 而给所有容器预留空间，可能造成大面积空白，影响感知体验。

取舍顺序建议如下：

1. 先保证 LCP、INP、CLS 三项达标，这是用户可感知的底线；
2. 再用 TTFB、FCP、TBT 做归因，确定瓶颈在服务端、资源加载还是主线程；
3. 最后用体积、请求数等成本指标设定预算，防止后续迭代悄悄回退。

指标是回归防线，不是优化目标本身。把 P75 达标写进发布卡点，比一次性冲高分更有价值。
