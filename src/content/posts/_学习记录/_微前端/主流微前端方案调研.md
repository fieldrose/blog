## 一、背景与约束

存量前端重构项目中，约 180 个异构业务以 iframe 形式嵌入主应用。这些业务分属不同团队、不同技术栈（jQuery、Vue2、原生 JS 并存），不在本次改造范围内，但需要继续与新版主应用共存。

集成约束有两条不可逾越的红线：

- 子应用不可改造：无权修改存量业务的 HTML Entry、构建配置和运行时代码
- 宿主零假设：集成形态需对宿主技术栈无感知，不能要求子应用主动配合

在这个前提下，微前端方案被纳入评估范围——目标是判断是否存在一种方案能让异构子应用"无感接入"新版主应用。

## 二、方案评估

### 2.1 qiankun

qiankun 是蚂蚁金服基于 single-spa 的封装，定位为生产可用的微前端框架。其核心机制是 HTML Entry：主应用通过 `fetch` 拉取子应用的 HTML，解析出 JS 和 CSS 资源后在沙箱中执行。

接入链路要求子应用配合实现三个生命周期钩子：

```ts
// 子应用需暴露的生命周期
export async function bootstrap() {}
export async function mount(props) {}
export async function unmount() {}
```

侵入点有三：

1. **构建产物**：子应用必须将打包格式改为 UMD（qiankun 2.x 兼容 ESM 但仍需导出生命周期），且资源路径需通过 `publicPath` 调整为运行时动态值
2. **入口文件**：子应用根组件需改造成可挂载 / 卸载的函数，而非直接 `createApp().mount()`
3. **静态资源**：CSS 会被 qiankun 抽取并加前缀隔离，但需要子应用提供正确的资源 URL

沙箱层采用 JS 沙箱（`Proxy` 代理 `window`，配合 `snapshot` 快照模式兼容低版本浏览器）和样式隔离（前缀 + `scoped` 两种模式）。

在存量场景下，三个侵入点全部不满足：子应用无法改造，构建链路不可控，入口文件不可动。qiankun 的接入前提是"子应用愿意配合"，与当前约束直接冲突。

### 2.2 SystemJS / single-spa

single-spa 是微前端的调度内核，SystemJS 是其加载器。与 qiankun 的区别是 single-spa 不处理样式隔离，只负责模块加载和生命周期调度。

接入链路同样要求子应用导出生命周期钩子，且构建产物需为 AMD 格式（SystemJS 默认支持）。侵入点与 qiankun 一致，但隔离能力更弱——样式隔离需自行实现（CSS Modules / Shadow DOM / BEM）。

SystemJS 的优势在于加载器层面：它可以加载 AMD、UMD、ESM 等多种格式的模块。但这个优势建立在子应用"构建产物可被识别"的前提下——存量业务打包格式各异（有的是 IIFE 全局变量、有的是 CommonJS），SystemJS 无法保证正确加载。

### 2.3 Web Components

Web Components 是浏览器原生规范，通过 Custom Elements 实现组件级封装。理论上的零侵入方案：子应用只需将自身包装为一个 Custom Element，宿主以 DOM 标签形式嵌入。

```html
<legacy-app base="/old-app/"></legacy-app>
```

但 Web Components 并非真正的零侵入：

1. **封装成本**：子应用需要自行实现 Custom Element 的生命周期（`connectedCallback` / `disconnectedCallback`），并处理样式封装（Shadow DOM 或 CSS 前缀）
2. **框架适配**：Vue2 等老框架对 Shadow DOM 支持不完善，React 17 之前也有已知问题
3. **运行时限制**：Shadow DOM 内部的全局样式重置、`document.querySelector` 的作用域边界等问题需要额外处理

在存量业务不可控的前提下，Web Components 仍然需要子应用配合改造封装层。

## 三、维度对比

| 维度                | qiankun                                | single-spa + SystemJS     | Web Components            | iframe              |
| :------------------ | :------------------------------------- | :------------------------ | :------------------------ | :------------------ |
| **子应用侵入度**    | 高（生命周期 + 构建格式 + publicPath） | 高（生命周期 + 构建格式） | 中（Custom Element 封装） | 零（直接嵌入）      |
| **运行时隔离**      | JS 沙箱 + 样式隔离                     | 无（需自行实现）          | Shadow DOM 原生隔离       | 进程级隔离          |
| **构建链路侵入**    | 需改 rollup / webpack 配置             | 需改打包格式              | 需加封装层                | 无                  |
| **协议依赖**        | 生命周期钩子                           | 生命周期钩子              | Custom Element 生命周期   | postMessage（可选） |
| **样式穿透风险**    | 低（前缀隔离）                         | 高（无隔离）              | 低（Shadow DOM）          | 无（天然隔离）      |
| **与 SPA 路由集成** | 可监听主应用路由                       | 可监听主应用路由          | 需自行桥接                | URL 独立            |

## 四、决策

三种微前端方案的共同前提是子应用"愿意接入"——要么改构建，要么加生命周期，要么封装 Custom Element。而当前项目的核心约束是子应用不可改造。

唯一满足"零侵入"的方案是 iframe。它的隔离能力来自浏览器进程，不依赖子应用配合任何协议，代价是交互深度受限（postMessage 而非直接函数调用）和 UI 一致性需要额外处理（高度自适应）。

具体决策见项目经历系列第四篇《[存量集成与灰度发布：iframe、多入口与回滚](/zh/posts/存量集成与灰度发布：iframe、多入口与回滚/)》。

## 小结

微前端是"统一技术栈 + 各团队自治"场景下的合理架构选择，其设计前提与本次项目的"存量不可改造"约束存在根本错位。评估结果并非否定微前端方案本身，而是确认了它不适用于当前约束条件。

技术选型的核心依据始终是约束——当子应用不可控时，隔离等级最高、侵入度最低的方案胜出。
