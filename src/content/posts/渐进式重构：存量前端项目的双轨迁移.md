## Table of contents

## 一、背景

**项目定位**：移动端 App 内嵌 H5，承担集成门户角色——对接约 180 个业务菜单、40 余个页面，绝大多数业务以 URL 为边界集成，覆盖一线作业与管理场景。

**既有技术栈**：jQuery（1.x 为主，3.x 混用）+ 基于 AMD 的自研组件库，多页应用（MPA），无构建工具，新增页面需手写 ES5；原生客户端分 Android / iOS / 鸿蒙三端，由其他团队维护，通过 WebView 向页面注入 window 方法供 H5 调用。

**运行环境约束**：客户端使用系统原生 WebView 内核，兼容下限由手持终端（PDA）锁定为 Android 6 / iOS 10。

**重构动机**：需求方开始重视该集成入口，要求在存量业务之外叠加数据看板、分析图表、功能管理、客服助手、AI 助手等新业务。既有架构经多轮迭代，且之前较边缘。无状态管理、无统一通信约定、无文档，业务全景仅能通过阅读源码还原，已无法承载增量需求。

**技术选型**：Vue 3 + Vite，配套 TypeScript 与 vue-router（初期引入 Pinia，后因状态量小改为 `ref` 模块单例，见功能点 5）。

**约束条件**：业务不可中断；既有客户端不在改造范围内；重构需与存量版本的日常迭代并行推进。

**投入**：约一年。

**目标**：在不停机、可回滚的前提下，渐进式迁移至 Vue 3 + Vite SPA 应用。

### 技术选型的四条理由

**一、团队与协作成本**

公司内部 Vue 生态的使用面更广，既有成员的技术储备、可复用的组件资产、调试习惯都偏向 Vue。重构需与存量业务并行推进，期间人员可能轮换，技术栈的可接续性比框架之间有限的性能差异更重要。React 同样可以满足技术要求，但在本项目场景下，JSX 与额外状态管理方案带来的迁移成本，没有对等的收益来抵消。

其他系统中已有的 Vue 2 业务或组件若需集成进本项目，可先经 `@vue/compat` 迁移构建过渡到 Vue 3，再以 Vue 3 组件的形式接入，避免项目内同时运行两套 Vue 运行时。

**二、构建链路的缺口正好被 Vite 覆盖**

存量项目没有构建工具，新增页面手写 ES5，代码复用只能依赖 AMD 模块加载。Vite 提供了完整链路——开发期基于 ESM 的按需编译与 HMR，构建期由 Rollup 产出可控产物，插件机制足以覆盖后续遇到的兼容、注入、分包需求。2025 年初 Vite 生态已较成熟，生产可用性不构成主要风险，选型时的顾虑集中在老内核兼容而非工具本身。

**三、老内核兼容有明确解法**

老内核兼容是选型中硬性约束最强的一项。`@vitejs/plugin-legacy` 产出 modern / legacy 双份 bundle，按 `targets` 注入 core-js 与构建产物所需运行时，平台 API（Custom Elements、Shadow DOM）再经 `additionalLegacyPolyfills` 手动补齐。Vue 3 自身依赖 Proxy，Chrome < 51 的 Proxy 实现不稳定，据此把「尽量兼容」收敛为可验证的下限：实测与版本收集后确定最低内核为 Chrome 51 / iOS 10.3（实现细节与遗留问题见功能点 2）。

**四、允许渐进式落地，而非一次性重写**

约束是业务不可中断，且重构需与存量迭代并行。Vue 3 可以挂载到存量页面的局部节点，也可以作为独立入口与存量 MPA 并存；配合双入口灰度与按角色放量，迁移被拆成可回滚的小步，出问题时由管理端改回首页地址即可退回，无需前端发版。存量业务继续以 iframe 集成，改造边界收敛在宿主侧。这一条决定方案是否可行，前三条影响的是代价大小。

### 未采用的方案

| 方案                          | 未采用的原因                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| 继续 jQuery + 自研 AMD 组件库 | 无状态管理、无通信约定、无文档，已无法承载看板、图表、AI 助手类增量需求                  |
| React                         | 团队接受度与维护成本更高；对存量页面做局部集成时胶水代码更多                             |
| Angular                       | 体积与学习曲线不适合移动端 WebView，团队无相关储备                                       |
| 微前端（qiankun 等）          | 存量已可由 iframe 承接，收益有限；且子应用需侵入式改造，老内核下运行时开销与调试成本偏高 |
| Svelte 等新框架               | 生态与团队储备不足，招聘与交接风险不可控                                                 |

### 选型的代价

- legacy 双产物使构建体积增加；降级行为在开发环境无法验证，需构建后用 `pnpm preview` 起静态服务，在本机安装的 Chrome 49 中验证（见功能点 2）
- Vue 3 的 Proxy 依赖把下限钉在 Chrome 51，低于该内核的终端不具备覆盖条件
- 初期引入的 Pinia 在状态量小时显得过度分层，后改为 `ref` 模块单例，这一调整发生在项目中期而非选型阶段

## 二、功能点重构

### 功能点 1：客户端三端桥接适配层

**背景**
客户端由原生团队维护。三端均通过 WebView 注入 window 方法供 H5 调用，但协议互不兼容：Android 与 iOS 功能对等而方法名、参数结构不同（`window.android.jumpNewTab(url, options, type)` 与 `window.ios.jumpNewOne({ url, options, type })`）；注入内容与页面层级绑定，客户端仅支持两层，登录初始化第一层，经客户端跳转打开新页后注入第二层，两层 API 差异显著；鸿蒙端基于第三方通信库，需先手动拉起通信、在回调中注册方法后方可调用。老版本中这些调用散落在各业务代码内，无统一入口。

**目标**
在不改造客户端的前提下，收敛客户端能力调用入口，屏蔽三端协议差异，统一 H5 侧写法。

**结果**

- 落地：新增 `clientFunction.js` 作为薄适配层，基于 UA 判定运行环境后分发到对应实现；首页加载时完成鸿蒙的通信初始化，并将三端方法统一挂载到 window，使业务代码只依赖统一入口。
- 取舍：三端固定、方法量有限，采用 if/else 分发而非抽象接口；其局限明确——新增平台或方法规模膨胀时需扩充分支，不利于后续维护。
- 遗留问题：鸿蒙环境下以 iframe 集成的其他页面和使用客户端方法打开的二级页面无法继承首页的初始化，需各自独立重复拉起通信，属该端通信模型的固有限制。
- 覆盖能力：页面跳转、回退、重新登录、退出、定位、设备标识（IMEI）、拍照等。

**落地实现**

```js
// env.js 判定运行环境（示意）
// 基于UA嗅探实现的简易客户端环境检测
export const isAndroid = /Android/i.test(navigator.userAgent);
export const isIOS = /iPhone|iPad|iPod/.test(navigator.userAgent);
export const isHarmony = /Harmony|harmony/i.test(navigator.userAgent);
```

```js
// clientFunction.js 分发逻辑（示意）
// 客户端方法的浅层适配层
import { isAndroid, isIOS, isHarmony } from "./env";

export function jumpNewTab(url, options, type) {
  if (isAndroid) return window.android.jumpNewTab(url, options, type);
  if (isIOS) return window.ios.jumpNewOne({ url, options, type });
  if (isHarmony) return window.harmony.jumpNewTab(url, options, type);
}
```

```js
// 业务组件内使用
import { jumpNewTab } from "@/utils/clientFunction";

jumpNewTab("xxxx/xxxx", { id });
```

#### 后续演进：基于DIP解耦客户端能力调用层

**痛点**

- 新增平台：客户端方法按平台差异化分发，每接入一个新平台（如鸿蒙或pc端），都需在 `env.js` 补判定、在 `clientFunction.js` 补分支，改动落在既有代码上——违反开闭原则。
- 新增方法：客户端能力有一百余项且随业务持续变化，每新增或调整一个方法，需在三端实现之外于分发函数内补一个分支，同样是对既有代码的修改。
- 调用耦合：业务层直接依赖 `window.android` / `window.ios` 等具体实现，与平台细节耦合——违反依赖倒置。

三者叠加，分发函数随平台与方法的增长持续膨胀，维护成本随之上升。

**演进方案**

1. 定义平台无关的抽象接口，只声明能力，不感知具体平台：

```ts
// bridges/types.ts（示意）
export interface ClientBridge {
  jumpNewTab(
    url: string,
    options?: Record<string, unknown>,
    type?: string
  ): void;
  back(): void;
  // 后续新增能力在此声明
}
```

2. 三端各自独立实现，按文件拆分维护（`bridges/android.ts` / `bridges/ios.ts` / `bridges/harmony.ts`），平台差异收敛在实现内部：

```ts
// bridges/android.ts（示意）
import type { ClientBridge } from "./types";

export const androidBridge: ClientBridge = {
  jumpNewTab(url, options, type) {
    window.android.jumpNewTab(url, options, type);
  },
  back() {
    window.android.back();
  },
};
```

```ts
// bridges/ios.ts（示意）：同一接口，内部映射为 iOS 的方法签名
import type { ClientBridge } from "./types";

export const iosBridge: ClientBridge = {
  jumpNewTab(url, options, type) {
    window.ios.jumpNewOne({ url, options, type });
  },
  back() {
    window.ios.goBack();
  },
};
```

3. 在唯一的组合根按环境选定实现并导出单一实例，平台判定只发生在此处：

```ts
// bridges/index.ts（示意）：唯一的平台判定点
import type { ClientBridge } from "./types";
import { androidBridge } from "./android";
import { iosBridge } from "./ios";
import { harmonyBridge } from "./harmony";
import { isAndroid, isHarmony } from "./env";

export const bridge: ClientBridge = isAndroid
  ? androidBridge
  : isHarmony
    ? harmonyBridge
    : iosBridge;
```

4. 业务层只依赖接口实例，调用处不再出现任何平台判断：

```ts
import { bridge } from "@/bridges";

bridge.jumpNewTab("/work-order/detail", { id });
```

**文件结构对比（示意）**

改造前：环境判定与全部客户端能力集中在同一模块，平台差异以 if/else 内联在分发函数中。

```
utils/
├── env.js            # 运行环境判定（UA 嗅探）
└── clientFunction.js # 客户端能力集中分发，内部按平台 if/else
```

改造后：接口与实现分离，三端各自独立文件维护，平台判定收敛到组合根。

```
bridges/
├── types.ts          # ClientBridge 接口定义（平台无关）
├── android.ts        # Android 实现
├── ios.ts            # iOS 实现
├── harmony.ts        # 鸿蒙实现
└── index.ts          # 组合根：按环境选定实现，导出唯一实例
```

新增平台时，只需新增 `bridges/<platform>.ts` 并在 `index.ts` 注册。

**收益**

- 新增能力：接口声明一处、三端各实现一次，调用方无分支；
- 新增平台：新增一个实现文件并在组合根注册一行，调用方与既有实现均不改动——对扩展开放、对修改关闭；
- 业务层依赖抽象接口，而非 `window.android` 等具体对象——依赖倒置。

**要点**：抽象层的价值在于让调用方不再做平台分支。若调用处仍 if/else 直接实例化具体实现，抽象层形同虚设，只是多了一层转发。

**说明**：该方案在重构初期评估过。由于重构与存量迭代并行、排期紧张，接口化拆分需额外抽象层与适配成本，最终仍以 `clientFunction.js` 的 if/else 分发落地，依赖倒置作为后续优化方向记录。

### 功能点 2：老内核兼容与构建降级

**背景**
客户端使用系统原生 WebView，内核版本低且不可控；兼容下限由 PDA 终端锁定为 Android 6 / iOS 10。PDA 设备均为 Android 系统，经真机测试，其 WebView 内核最低为 Chrome 51。既有项目以无构建工具 + 手写 ES5 规避该问题，不具备现代构建能力。

**目标**
在引入 Vite 与 Vue 3 的前提下，保证目标内核可正常运行。

**结果**

- 选型：`@vitejs/plugin-legacy` 产出 legacy 双份产物，并按 `targets` 注入 core-js polyfill。WebView 内核下限取 Chrome 51 / iOS 10.3。

```js
// vite.config.ts
import { legacy } from "@vitejs/plugin-legacy";

export default {
  plugins: [
    legacy({
      // 目标内核下限，理由见「技术选型的四条理由」
      targets: ["chrome >= 51", "ios_saf >= 10.3", "not dead"],
      // 构建期无法推导的平台 API，需显式声明
      additionalLegacyPolyfills: [
        "@webcomponents/custom-elements",
        "@webcomponents/shadydom",
      ],
    }),
  ],
};
```

- 其他问题：需集成公司提供的 Web Components 组件库，但组件库仅发布构建产物、源码不可修改，须经 `additionalLegacyPolyfills` 注入平台 API polyfill。

**vite-legacy 插件边界与 polyfill**

各类特性的归属与处理方式：

| 特性类型         | 归属                 | 示例                       | 处理方式                      |
| :--------------- | :------------------- | :------------------------- | :---------------------------- |
| JS 语法 (Syntax) | Babel Transform      | `class`, `?.`, `const`     | 编译时转译，与 core-js 无关   |
| JS 内置对象/方法 | core-js              | `Promise`, `Array.flat`    | 运行时注入（Polyfill）        |
| Web/DOM API      | 独立 Polyfill        | `fetch`, `WebComponents`   | 需手动引入，不在 core-js 范围 |
| CSS 特性         | PostCSS/Autoprefixer | `flexbox`, `grid`, `:host` | 构建时处理，与 JS 无关        |

- **成因**：core-js 的模块表对应 ECMAScript 规范与 TC39 提案；Web Components、DOM、`fetch` 等由 WHATWG / W3C 定义，属宿主环境能力，不在表内。`useBuiltIns: 'usage'` 的「扫描源码 API 名 → 查 `core-js-compat` 表」链路因此无匹配入口——并非运行时判断不出缺失，而是构建期没有查询路径。
- **两个正交维度**：能否 polyfill 取决于是否可用旧 API 等价实现（`Proxy`、`BigInt`、`WeakRef` 均在 ECMAScript 范围内但不可实现，`Symbol` 可模拟但有损），与规范归属无关——平台 API 的问题在归属，语言新特性的问题在可行性。
- **插件范围**：`@vitejs/plugin-legacy` 覆盖四块——语法转译（babel）、ES API 补齐（core-js，继承上述边界）、转译产物运行时（`regenerator-runtime` / `@babel/runtime`）、加载机制（`module` / `nomodule` 双发、Safari 10.1 兼容补丁、SystemJS 兜底）。范围外的平台 API 仅经 `additionalLegacyPolyfills` 手动注入，该选项本身即边界的体现。
- **另注**：legacy 产物仅在构建后生效，开发环境无法验证降级行为。当时的验证方式是执行 `pnpm build` 后用 `pnpm preview` 起本地静态服务，在本机额外安装的 Chrome 49 中打开页面，确认 legacy bundle 的加载与运行情况。

#### 要点提取：webcomponents 组件集成排查与解决方向

定位缺失能力，按需补齐。

**定位**：WebView 远程调试需依赖真机——Android 需客户端开启 `setWebContentsDebuggingEnabled(true)` 后通过 `chrome://inspect` 连接，iOS 需 `isInspectable` 后通过 Safari Inspector 连接。当时缺少真机，无法走远程调试。替代方案是注入全局错误上报，并在真机运行能力探针，逐项确认缺失的平台 API：

```js
// 能力探针（示意）：真机运行后回传
const probe = {
  customElements: "customElements" in window,
  attachShadow: !!Element.prototype.attachShadow,
  adoptedStyleSheets: "adoptedStyleSheets" in Document.prototype,
  resizeObserver: "ResizeObserver" in window,
};
```

**补齐**：按探针结果针对性引入。

| 缺失能力           | polyfill                          |
| ------------------ | --------------------------------- |
| Custom Elements v1 | `@webcomponents/custom-elements`  |
| Shadow DOM v1      | `@webcomponents/shadydom`         |
| adoptedStyleSheets | `construct-style-sheets-polyfill` |
| ResizeObserver     | `resize-observer-polyfill`        |

集成方式：通过 `additionalLegacyPolyfills` 注入，仅存在于 legacy bundle。modern bundle 用户（Chrome 61+）原生支持 Custom Elements / Shadow DOM，不会加载这些 polyfill；legacy bundle 用户（Chrome 51-60）均需 polyfill，故运行时按需检测无收益，直接注入更可靠。`webcomponents-loader.js` 的按需加载方案需等待 `WebComponentsReady` 事件，与不可控的第三方组件库初始化时机冲突，未采用。

**限制**：`shadydom` 在 DOM API 层实现隔离，老设备高频渲染有性能损耗；`:host`、`::slotted`、CSS 变量等样式层能力无法完全 polyfill，降级内核上隔离会失真。

**上游方向**：问题根源在组件库的构建产物——宿主侧只能补平台 API，以下四项均不可及：

- 语法层：polyfill 以解析为前提，webpack 按现代 target 打包残留的 `async/await`、可选链等语法在老内核直接 `SyntaxError`，只能由 Babel 在构建期转译。
- 语义层：Shadow DOM 无等价实现，`shadydom` 的样式作用域与事件重定向均为近似模拟；上游可改实现（关闭 Shadow DOM 改用 scoped CSS）绕开，宿主侧只能接受失真。
- 时序层：patch 必须先于 `customElements.define` 与组件实例化执行，组件库自带 bootstrap、内部再分包时，宿主难以保证加载顺序。
- 作用域层：`shadydom` patch 整页 DOM 与事件系统，开销覆盖全部业务代码；上游做双产物可让新内核零加载，并在 legacy 产物内裁剪不需要的能力。

由此两条路径：一是由组件库维护方调整构建配置，在 Babel targets 中纳入老内核并内联所需 polyfill，属根治方案——修复一次覆盖所有接入方，且可纳入其真机测试矩阵；二是维持宿主侧 `additionalLegacyPolyfills` 兜底，成本低、见效快，但受限上述四点。依赖面小时也可改用 Vant 或自研组件绕开。

### 功能点 3：路由与导航体系

**背景**
老版为 MPA：底部导航四个 tab 对应四个 HTML，首页上方整块 iframe，切换 tab 即替换 iframe 的 `src`；页面跳转依赖客户端方法（覆盖当前页打开新页）或直接替换 URL；WebView 内无有效的 history 栈。

**目标**
以 SPA 方式重建页面内导航，并在既有限制下选择可落地的路由模式。

**结果**

- 约束：生产侧存在互联网暴露面管控，服务端仅放行预先登记的路径与静态资源 URL，其余一律拦截。移动端边缘手势由客户端识别，识别后通过 `window` 回调通知 H5 执行后退 / 前进。
- 选型分析：history 模式的核心收益（URL 分享、浏览器前进后退）在 WebView 中本就被客户端方法接管，收益有限；同时构建产物带内容哈希，每次构建均需重新登记暴露面白名单，history 的路由 URL 同样会被拦截，维护成本高。
- 结论：采用 vue-router 的 memory 模式，固定入口 URL，规避白名单逐次登记与路由拦截。
- 问题与处理：memory 模式不对外暴露完整路由栈（公开接口仅 `back` / `forward` 与当前 location）。手势由客户端识别后回调 H5，H5 需判断当前是否可退 / 可进并执行对应跳转，同时把栈状态回传客户端以控制手势可用性，故以响应式数组自行维护栈。

```ts
// RouterItem type.ts
interface RouteItem {
  path: string;
  name: string;
  component: () => Promise<Component>;
}

// 手动路由栈（示意）：memory 模式取不到内部栈，只能自行记录
const routeStack = ref<RouteItem[]>([]);

function onRouteChange(item: RouteItem) {
  routeStack.value.push(item); // 跳转、模块切换时调用
  syncStackState(); // 把栈状态回传客户端，控制手势可用性
}

// 客户端识别手势后调用，由 H5 判断是否可执行
window.userBack = () => {
  if (routeStack.value.length > 1) {
    routeStack.value.pop();
    router.back();
    syncStackState();
  }
};

window.userForward = () => {
  // forward 需要额外记录前进栈，示意略
  router.forward();
  syncStackState();
};

function syncStackState() {
  // 调用客户端方法上报栈深度，由客户端决定是否启用边缘手势
  window.client.updateStackState(routeStack.value.length);
}
```

### 功能点 4：状态管理重构

**背景**
老版无状态管理，用户态与业务态分散在 URL query、cookie、storage 及各模块内部，跨页面共享依赖隐式约定；登录态由客户端登录后经 URL 携带的 token 提供，前端不存在登录接口。

**目标**
收敛为单一数据源，并与「进入即携带新 token」的会话模型对齐。

**结果**

- 落地：初期引入 Pinia，但状态量小（token、开关、权限等）且为内存态，Pinia 的 store / getter / action 分层显得过度，团队 TS 熟练度也增加了类型推导成本。后改为 `ref` 模块单例作为全局状态，组件内直接 import 使用，去掉了 Pinia 的概念分层。
- 迭代：token 初始统一存于 storage，上线后有用户反馈异常；最终收敛为内存态——每次进入页面均由客户端携带新 token 下发，内存态与会话生命周期一致，也规避了持久化导致的脏数据问题。
- TypeScript 策略：团队 TS 熟练度不一，仅对路由栈、客户端方法桥接等底层模块使用 TS，业务层保持 JS。

```ts
// stores/global.ts（模块单例）：Vue 响应式对象脱离组件后依然生效，导出即全局共享
import { ref } from "vue";

interface UserInfo {
  id: string;
  name: string;
}

interface GlobalState {
  token: string;
  switches: Record<string, boolean>;
  permissions: string[];
  user: UserInfo | null;
}

const createInitialState = (): GlobalState => ({
  token: "",
  switches: {},
  permissions: [],
  user: null,
});

export const globalState = ref<GlobalState>(createInitialState());

export function setToken(token: string) {
  globalState.value.token = token;
}

export function clearSession() {
  globalState.value = createInitialState();
}
```

组件内直接 import，无需 `useStore()`：

```ts
import { globalState, setToken } from "@/stores/global";

const token = computed(() => globalState.value.token);
setToken(newToken);
```

也可以将部分业务独有的状态按组合式函数（hooks）封装：

```ts
// usePermission.ts
import { computed } from "vue";
import { globalState } from "@/stores/global";

export const usePermission = () => {
  const token = computed(() => globalState.value.token);
  const hasPermission = (code: string) =>
    globalState.value.permissions.includes(code);

  return {
    token,

```

业务层解构使用：

```js
const { token, hasPermission } = usePermission();
```

### 功能点 5：存量业务集成策略

**背景**
约 180 个外接业务以 URL 为边界，多为异构系统，大量以 iframe 内嵌；iframe 与宿主页通过 `window.parent` 直接通信，无统一协议，耦合且分散。

**目标**
明确新业务与存量业务的集成边界，控制改造范围与成本。新项目中，iframe 的集成需要自适应高度以避免滚动条问题，并与父页面的视觉效果保持一致。

**结果**

- 否决微前端：评估 qiankun 与 SystemJS，二者均要求对子应用做侵入式改造（HTML Entry、构建产物格式等）；在存量系统不可控、改造面过大的前提下成本不可行。
- 结论：保留 iframe 作为存量集成手段；新业务在 SPA 内以 vue-router 站内切换实现类原生过渡，老业务通过客户端方法打开新 tab 并指定 URL。
- 一致性：所有跨域（接口与 iframe）由后端转发收敛为同源，规避跨域与鉴权问题；iframe 高度自适应统一由父页面接管——同源下直接观察内部 document（MutationObserver + ResizeObserver，必要时按需轮询兜底），跨域场景才需子页面 `postMessage` 上报。
- 边界：新版接管入口、角色、卡片渲染与新增业务，存量异构系统继续以 URL 为边界集成。

#### 要点提取：iframe 业务集成

**背景**
新项目中需要集成老业务，代码量较大，且分散在不同系统，无法做微前端改造。依旧选用 iframe 作为主要的集成手段。

**目标**
新项目中使用 iframe 集成的内容粒度更细，例如组件级集成，原有的页面级集成部分保留。且组件级集成需要父页面 iframe 元素根据加载内容自适应宽高（此处宽度一般固定为 100%，高度根据内容自适应），以保证和新项目一致的视觉效果。

**结果**
iframe 高度自适应是集成的经典问题，解决方案一般分为同源和跨域两个部分。新项目中所有 iframe 都是同源的（由后端转发收敛为同源），父页面可直接读取 `contentDocument` 操作内部 DOM。

对于同源 iframe 集成，`MutationObserver`（Chrome 18 / IE 11 起）覆盖 DOM 结构变化；`ResizeObserver`（Chrome 64 / Safari 13.1 起，低于项目 targets）覆盖尺寸变化，已通过 legacy 插件注入 polyfill。两者均无法感知 `overflow: hidden` 等导致的 border box 与 `scrollHeight` 不一致，由按需轮询兜底。

对于跨域 iframe 集成，一般只能通过子页面 postMessage 主动上报内容高度，父页面监听消息，实时更新 iframe 高度。

最终使用 MutationObserver + ResizeObserver + 轮询兜底的组合，实现 iframe 高度自适应。

核心逻辑抽离为独立工具函数，Vue 组件只负责生命周期管理和 props 透传：

```ts
// utils/iframeResize.ts
interface ResizeOptions {
  enablePolling?: boolean; // 是否开启轮询兜底（body 有 overflow 的存量页面开）
  pollingInterval?: number; // 轮询间隔 ms，默认 2000
  onHeightChange?: (h: number) => void;
}

/**
 * 同源 iframe 高度自适应。父页面直接操作 iframe.contentDocument，无需子页面配合。
 * ResizeObserver 覆盖尺寸变化（图片/字体/CSS 过渡）；
 * MutationObserver 覆盖 DOM 变化（JS 渲染列表、SPA 路由切换）；
 * 轮询兜底仅在 enablePolling=true 时开启，用于 body overflow 导致 border box 与 scrollHeight 不一致的场景。
 * 返回 cleanup，组件卸载时调用。
 */
export function setupIframeAutoResize(
  iframe: HTMLIFrameElement,
  options: ResizeOptions = {}
): () => void {
  const {
    // 只对指定 iframe 开启轮询兜底，默认不开启，以节省低版本浏览器的性能
    enablePolling = false,
    pollingInterval = 2000,
    onHeightChange,
  } = options;
  let lastHeight = 0;
  let mo: MutationObserver | null = null;
  let ro: ResizeObserver | null = null;
  let timer: number | null = null;

  const update = () => {
    const doc = iframe.contentDocument;
    if (!doc) return;
    const h = doc.documentElement.scrollHeight;
    if (h !== lastHeight) {
      lastHeight = h;
      iframe.style.height = h + "px";
      onHeightChange?.(h);
    }
  };

  const cleanup = () => {
    mo?.disconnect();
    ro?.disconnect();
    if (timer) clearInterval(timer);
  };

  iframe.addEventListener("load", () => {
    const doc = iframe.contentDocument;
    if (!doc) return;
    if (typeof ResizeObserver !== "undefined") {
      ro = new ResizeObserver(update);
      ro.observe(doc.body);
    }
    mo = new MutationObserver(update);
    mo.observe(doc.body, { childList: true, subtree: true });
    if (enablePolling) timer = window.setInterval(update, pollingInterval);
    update();
  });

  return cleanup;
}
```

Vue 组件封装，按需开启轮询：

```vue
<!-- 通用 iframe 组件 IframeBox.vue -->
<script setup lang="ts">
import { ref, onMounted, onUnmounted } from "vue";
import { setupIframeAutoResize } from "@/utils/iframeResize";

const props = defineProps<{
  src: string;
  enablePolling?: boolean;
  pollingInterval?: number;
}>();

const iframeRef = ref<HTMLIFrameElement | null>(null);
let cleanup: (() => void) | null = null;

onMounted(() => {
  if (iframeRef.value) {
    cleanup = setupIframeAutoResize(iframeRef.value, {
      enablePolling: props.enablePolling,
      pollingInterval: props.pollingInterval,
    });
  }
});

onUnmounted(() => cleanup?.());
</script>

<template>
  <iframe
    ref="iframeRef"
    :src="src"
    frameborder="0"
    style="width: 100%; height: 0"
  />
</template>
```

```vue
<!-- 业务模块使用：新页面不开轮询；存量页面不可控时兜底 -->
<IframeBox src="/new/dashboard" />
<IframeBox src="/old/legacy" :enable-polling="true" />
```

**补充说明**

iframe 高度自适应属于经典问题，有较为成熟的第三方解决方案，如 [iframe-resizer](https://iframe-resizer.com/) 等。

因项目场景为同源 iframe 集成，仅需高度自适应。不需要过多的边界处理（例如：打印模式、iOS Safari 弹性滚动、字体闪烁、SPA hash 路由等），且第三方组件较重。故选择手动实现。

### 功能点 6：首页卡片化与角色驱动渲染

**背景**
老项目首页以 grid 布局的菜单列表为主（icon + 名字 + 用户权限锁），点击直接走客户端方法跳转。无明确角色与权限体系——大体上所有用户共用同一份菜单列表，部分菜单点开后才显示业务下线或权限不足。菜单由后端接口返回，后台管理页面维护数据库实现增删改。

新项目为 SPA，底部导航承载多个入口，新增首页以卡片列表的形式承载新的业务模块和旧的存量系统（iframe 集成的存量系统页面），菜单列表作为独立页面组件。新项目引入了明确的用户角色体系，每个角色需要对应不同的卡片列表。

**目标**

1. 数据驱动卡片渲染：后端返回顺序即渲染顺序，前端维护卡片 id → 组件的映射关系；
2. 角色驱动内容差异：后端按角色返回不同卡片列表，角色差异化内容由后端定义；
3. 用户自定义偏好：拖拽排序、显隐控制（角色对应的卡片集合固定，用户仅决定哪些展示）；偏好存后端以支持多设备切换同步；
4. 权限前置拦截：卡片按 `type` 字段标记所需权限，未授权前卡片正常展示但右下角加锁图标，点击拦截跳转认证页面，完成后回到原目标。

**结果**

- **接口调用顺序**：角色查询接口优先返回当前用户角色标识，随后以角色为参数调用卡片列表接口，后端按角色过滤并返回卡片数组（返回顺序即渲染顺序）。
- **卡片结构**：后端返回形如 `[{ id, type, needRefresh, ... }, ...]`，其中 `type` 对应所需权限类型，前端根据已获取的权限状态决定锁图标是否展示。
- **权限拦截流程**：点击卡片时检查 `type` → 无权限则拦截并跳转认证页面 → 记录待跳目标 → 认证完成后自动恢复原跳转。
- **用户自定义偏好**：拖拽排序与显隐设置存入后端，多设备登录时自动同步布局。
- **接口全为新写**：角色查询、卡片列表、认证接口均为新项目新增，不复用老项目的菜单接口。

### 功能点 7：灰度发布与双轨部署

**背景**
新旧两套前端并存，登录入口由客户端发起、后端返回首页地址决定。发布链路受网络环境限制，无 CI，采用零信任客户端接入 + SFTP 逐台替换 8 台主机的对应目录（`/oneapp` 与 `/newoneapp` 分目录存放）。

**目标**
在不中断业务、可随时回滚的前提下完成放量切换。

**结果**

- 落地：新旧版本位于同域名不同路径，生产环境同时部署；管理端按角色调整登录接口返回的首页地址即可完成切换与回滚，无需前端发版。
- 节奏：先以测试白名单放量，再按角色分批放开（管理类角色优先，逐步扩展至一线角色），最终全量切换。
- 代价：放量期间新功能需双轨实现——新版以 Vue 开发，旧版仍需手写 ES5；发布为纯手工流程，且构建产物哈希变化需逐次登记暴露面白名单（后以自研 Vite 插件自动化，见《[双轨迁移的工程化配套实践](/zh/posts/双轨迁移的工程化配套实践/#四暴露面清单自动化自研-vite-插件)》）。

## 三、最终效果

- **工程化**：从无构建工具的 jQuery + AMD MPA 转为 Vue 3 + Vite SPA，具备依赖管理、模块化打包与 HMR；组合式 API 复用逻辑，路由栈、客户端桥接等底层模块以 TS 约束。
- **状态收敛**：分散在 URL query / cookie / storage 及各模块内部的用户态收敛为 `ref` 模块单例；token 收敛为内存态，与「进入即携带新 token」的会话模型对齐，规避持久化脏数据。
- **路由与桥接**：vue-router memory 模式固定入口 URL，规避暴露面白名单逐次登记，手动路由栈支撑客户端手势回退；三端客户端方法收敛为统一适配层，屏蔽 Android / iOS / 鸿蒙协议差异。
- **兼容性**：`@vitejs/plugin-legacy` 双产物覆盖 WebView 内核下限 Chrome 51 / iOS 10.3（语法转译 + core-js + 平台 API polyfill）；Web Components 组件库在老内核下的样式失真与性能损耗为遗留项。
- **存量集成**：约 180 个外接业务以 iframe + 后端同源转发保留集成，高度自适应由 MutationObserver + ResizeObserver + 按需轮询实现；未引入微前端，改造边界收敛在宿主侧。
- **业务承载**：首页重构为卡片化工作台——角色驱动渲染、权限前置拦截（认证后恢复原跳转）、用户偏好存后端多端同步；数据看板、AI 助手等新增业务全部落在新版，迁移完成后迭代全部在新版进行。
- **交付模式**：双入口灰度（`/oneapp` / `/newoneapp`）按角色分批放量，管理端切换登录返回的首页地址即可回滚，无需前端发版；约一年完成全量迁移，全程未停机。
