## 一、环境约束

项目的工程化方案由三组硬约束决定：

- **内网隔离**：客户侧网络仅放行指定 IP（生产服务器）访问数据库与业务系统，本地机器与独立测试环境的接口均调不通——数据源只能由生产服务器触达。
- **无 CI**：发布为手工流程，产物经 SFTP 逐台上传。
- **互联网暴露面管控**：生产侧仅放行预先登记的 URL，其余一律拦截。

三者叠加的结果：日常测试复用生产网络权限（平行测试目录）、特殊场景需经 Docker 镜像交付、本地联调依赖代理与协议对齐、发布登记需要自动化。

## 二、测试环境：常态与特殊场景

**平行测试环境（常态）**

日常测试走这条线——借用生产服务器的网络权限：在生产服务器上与生产目录平级部署一套平行目录，生产 `/newoneapp/`，测试 `/newoneappdev/`。前后端同机部署，复用生产机器的网络权限与域名证书，入口不对真实用户开放。过渡期新旧两版并存，实际维护四套目录：`/oneapp`、`/oneappdev`、`/newoneapp`、`/newoneappdev`。

**测试专用客户端包**：单独打一份首页地址固定指向平行测试目录的客户端包，仅分发给测试人员；测试与生产共用大部分数据。

**Docker 镜像交付（特殊场景）**

公司流程要求通过 Harbor 镜像更新时走这条线，日常不使用。老项目代码即经此部署，后延续到新项目的测试版本代码。前端侧发布流程：本地构建产物，Dockerfile 以 dist 目录为产物源构建镜像，登录 Harbor 推送，测试环境拉取运行；全流程封装为 sh 脚本一键执行，镜像名经终端交互生成。

受内网隔离限制，容器无法触达生产数据与接口，测试数据由后端提供或前端 mock——功能可验证，真实数据的联调不可用。

```dockerfile

COPY dist/ /usr/share/nginx/html/newoneappdev/
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

## 三、本地联调：代理与协议对齐

**背景**
本地 localhost 需要调用生产、测试或后端同事本地的接口，直接请求存在跨域；且线上统一升级 https 后，本地 http 开发环境出现协议不一致问题。

**结果**

- **跨域**：`server.proxy` 按前缀代理，接口地址在业务代码中收敛为相对路径，跨域消解在 dev server 转发层；`target` 经环境变量注入，按数据源（生产 / 测试 / 同事本地）切换。

```ts
// vite.config.ts（示意）
import { defineConfig, loadEnv } from "vite";
import basicSsl from "@vitejs/plugin-basic-ssl";

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd());
  return {
    // 协议对齐：dev server 以 https 运行，首次访问需手动信任证书
    plugins: [basicSsl()],
    server: {
      proxy: {
        "/api": {
          target: env.API_TARGET,
          // 网关按 Host 分发路由时需要改写
          changeOrigin: true,
          // 目标为自签 / 内网证书时跳过校验，否则代理返回 502
          secure: false,
        },
      },
    },
  };
});
```

- **协议对齐**：线上升级 https 后，http 页面与 https 接口混用受浏览器安全策略限制（mixed content）。`@vitejs/plugin-basic-ssl` 为 dev server 签发自签证书，本地以 https 运行，与线上协议对齐；浏览器首次访问需手动信任证书。

## 四、暴露面清单自动化（自研 Vite 插件）

**背景**
暴露面管控要求逐次登记产物 URL，而前端产物带内容哈希——每次发版文件名全变，清单需整批重出；过渡期四套目录并存，手工整理易漏。登记入口为既有管理后台：按项目维度维护（本项目对应多台服务器），按公司默认目录结构拼接完整地址；仅支持精确 URL，不支持前缀通配。

在项目迭代过程中，每次发版都需要手动登记暴露面，这既耗时又易漏。因此，我们自研了一个 Vite 插件，自动产出可上传的登记清单，消除手工整理。

**目标**
构建完成后自动产出可上传的登记清单，消除手工整理。

**结果**

- 以标准 Vite 插件实现（`apply: "build"`）：在 `writeBundle` 钩子遍历产物文件名；
- 登记项 = 统一前缀目录 + 产物文件名，经 `xlsx` 生成表格文件；
- 增量语义由管理后台的去重承担，插件无需处理与历史清单的合并。

```ts
// vite-plugin-vue-exposure-list.ts（示意）
import type { Plugin } from "vite";
import * as XLSX from "xlsx";

export function exposureList(prefix: string): Plugin {
  return {
    name: "vite-plugin-vue-exposure-list",
    apply: "build",
    writeBundle(_options, bundle) {
      // 遍历产物文件名（含内容哈希），拼接统一前缀目录即为登记项
      const rows = Object.keys(bundle)
        .filter(name => !name.endsWith(".map"))
        .map(name => ({ path: `${prefix}/${name}` }));

      const ws = XLSX.utils.json_to_sheet(rows);
      const wb = XLSX.utils.book_new();
      XLSX.utils.book_append_sheet(wb, ws, "exposure");
      XLSX.writeFile(wb, "exposure-list.xlsx");
    },
  };
}
```

```ts
// vite.config.ts（示意）
import vuePlugin from "vite-plugin-vue-exposure-list";

export default defineConfig({
  // 注册插件，指定统一前缀目录
  plugins: [vuePlugin("/xxx/xxx/xxx")],
});
```

**局限**：清单粒度是精确 URL，管理后台不支持目录级前缀放行，产物数量增长时登记项数量同步膨胀——这是管控侧的限制，插件只能做到「不再漏登」。

## 五、测试体系（演进方向）

**现状**

项目无自动化测试，回归依赖人工与平行测试目录真机验证。存量部分为 jQuery MPA，不在改造范围内——测试体系只针对新 SPA。

**分层选型**

| 层        | 工具                                   | 覆盖对象                                 | 落地条件                     |
| :-------- | :------------------------------------- | :--------------------------------------- | :--------------------------- |
| 单元      | Vitest                                 | 纯函数：token 解析、路由栈判断、权限判定 | 无依赖，可先行               |
| 逻辑/组件 | Vitest + happy-dom + `@vue/test-utils` | hooks、视图组件                          | 需初始化全局状态并 mock 网络 |
| 端到端    | Playwright                             | 页面级主流程                             | 需 mock 后端，且无法覆盖真机 |

选 Vitest 的理由是与 Vite 同源：`resolve.alias`、`define`、环境变量直接复用，无需另建转译配置，TS / ESM 原生支持。需注意 `@vitejs/plugin-legacy` 面向构建产物，测试模式应跳过或单列配置。

```ts
// vitest.config.ts（示意）：与 vite.config 分离，legacy 与 proxy 配置不进入测试模式
import { fileURLToPath } from "node:url";
import { defineConfig } from "vitest/config";
import vue from "@vitejs/plugin-vue";

export default defineConfig({
  plugins: [vue()],
  resolve: {
    // 与 vite.config 保持同一 alias 约定
    alias: { "@": fileURLToPath(new URL("./src", import.meta.url)) },
  },
  test: {
    environment: "happy-dom",
    setupFiles: ["./tests/setup.ts"],
  },
});
```

```ts
// src/lib/__tests__/parseToken.spec.ts（示意）：纯函数层，无环境依赖
import { describe, expect, it } from "vitest";
import { parseToken } from "../parseToken";

describe("parseToken", () => {
  it("从查询串中取出 token", () => {
    expect(parseToken("?token=abc123&from=oa")).toBe("abc123");
  });

  it("缺失时返回 null", () => {
    expect(parseToken("?from=oa")).toBeNull();
  });
});
```

```ts
// src/stores/__tests__/usePermission.spec.ts（示意）：hooks 层
import { beforeEach, describe, expect, it } from "vitest";
import { clearSession, globalState } from "@/stores/global";
import { usePermission } from "@/stores/usePermission";

describe("usePermission", () => {
  // 全局单例跨用例共享，必须显式重置——隐式契约在测试中的直接代价
  beforeEach(() => clearSession());

  it("会话未初始化时拒绝访问", () => {
    expect(usePermission().canAccess("dashboard")).toBe(false);
  });

  it("初始化后按权限放行", () => {
    globalState.value = { ...globalState.value, permissions: ["dashboard"] };
    expect(usePermission().canAccess("dashboard")).toBe(true);
  });
});
```

**E2E 的边界**

端到端在此项目只能覆盖部分事实，边界需写明，否则会误判「测试通过」的含义：

- **内核**：Playwright 自带 Chromium 远高于兼容下限 Chrome 51，通过不代表老内核可用；兼容性仍由真机验证——与[主文章](/zh/posts/渐进式重构：存量前端项目的双轨迁移/)的 legacy 结论一致，降级行为本身无法在开发环境验证。
- **运行宿主**：真实形态是客户端 WebView 内嵌，客户端注入的 `window.android` / `window.ios` / `window.harmony` 在浏览器中不存在，需以 module mock 替换客户端能力模块——无需为可测性引入 DIP，模块替换已足够。
- **数据源**：内网隔离下测试环境调不通生产接口，E2E 须拦截并 mock HTTP（msw 或 route interception）；真实链路只能由平行测试目录人工回归。

```ts
// e2e/grid.spec.ts（示意）：不启动真实后端，桥接能力以桩函数补齐
import { expect, test } from "@playwright/test";

test.beforeEach(async ({ page }) => {
  // 客户端注入在浏览器中不存在，按 ClientBridge 的形状补齐
  await page.addInitScript(() => {
    (window as any).android = { jumpNewTab: () => {}, back: () => {} };
  });
});

test("按 token 拉取用户信息并渲染网格", async ({ page }) => {
  await page.route("**/api/user/info*", r =>
    r.fulfill({ json: { id: "u-1" } })
  );
  await page.route("**/api/grid/marketing*", r =>
    r.fulfill({ json: { items: [{ id: 1, title: "示例指标" }] } })
  );

  await page.goto("/grid/?token=test-token");
  await expect(page.getByRole("heading", { name: "示例指标" })).toBeVisible();
});

test("token 缺失时渲染错误态", async ({ page }) => {
  await page.goto("/grid/");
  await expect(page.getByText("缺少访问凭证")).toBeVisible();
});
```

**mock 的边界**：mock 网络层，不 mock 全局状态与 hooks。前者是外部依赖，后者是待测逻辑——把全局状态一并 mock 掉，验证的是 mock 自身的形状，而非真实的装配时序（时序问题见「对外集成页」一节）。

**引入顺序**：纯函数 → hooks → 组件 → E2E。其中 hooks 一层会直接暴露全局单例的初始化时序依赖，是收益与成本的分界点。

**为何未落地**：测试的价值主要由 CI 门禁兑现——无 CI 时测试只能手动触发，回归收益折半；E2E 又覆盖不到真实运行环境（WebView、老内核、内网数据源），投入产出比不足以排在双轨迁移与业务交付之前。作为演进方向记录，实施前提是先补齐 CI。

## 六、CI/CD：现状与演进方向

**现状**

代码托管在公司内网 GitLab，构建在本地执行。测试环境经公司 Harbor 分发 Docker 镜像（见第二节）；生产环境产物经甲方提供的 SFTP 客户端上传，再经另一款甲方工具登录服务器执行发布命令。按定义，CI（持续集成，提交后自动构建与验证）与 CD（持续交付，产物自动流转至发布）均未闭环，发版全程人工串接。

**演进方向**

同一组内网约束下，可行路径是「构建留内网、部署标准化」：

- **构建闭环**：GitLab CI + 自建 runner 在内网完成构建，npm 依赖走内网镜像源，构建过程不触达外网；测试接入后，单元与组件测试可作为流水线的验证环节，E2E 因依赖环境需单列流水线；
- **制品包交付**：产物收敛为版本化的单一制品包，上传后执行固定部署脚本——部署动作从零散文件加人工记忆变为标准制品；
- **不在生产服务器构建**：构建峰值占用生产资源、引入 Node 运行时需审批、npm 依赖需离线化安装、构建环境意味着源码出域——四项成本均落在生产侧，构建留在内网是唯一低成本选项。

```yaml
# .gitlab-ci.yml（示意）：内网 runner 闭环构建，产出为版本化制品包
stages:
  - verify
  - build

unit:
  stage: verify
  tags: [intranet] # 内网自建 runner，无外网出口
  script:
    - pnpm install --frozen-lockfile # registry 指向内网镜像源
    - pnpm vitest run
  artifacts:
    when: always
    reports:
      junit: coverage/junit.xml

build:
  stage: build
  tags: [intranet]
  needs: [unit]
  script:
    - pnpm build
    - tar -czf "dist-${CI_COMMIT_SHORT_SHA}.tar.gz" -C dist .
  artifacts:
    paths:
      - "dist-*.tar.gz"
      - exposure-list.xlsx # 暴露面清单随制品一同产出
```

E2E 依赖运行环境而非构建产物，需单列流水线，不与上述阶段串联。

部署的最后一跳（文件在生产服务器落位）仍需人工完成，这是客户侧流程决定的上限。

**为何未落地**：单项目体量下本地构建成本可控，发布频率未使其成为瓶颈，属效率改善项而非阻塞项——与[主文章](/zh/posts/渐进式重构：存量前端项目的双轨迁移/)中 DIP 方案的取舍同理，作为演进方向记录。

## 七、对外集成页：URL 形态的多入口方案

**背景**

主应用采用 vue-router 的 memory 模式，页面层级由路由栈管理，深层页面没有对应 URL；而公司层面对外集成统一要求提供 URL，由各宿主系统以 iframe 嵌入。宿主技术栈异构——jQuery、Vue2、React 并存，集成形态需对栈零假设。

**形态对比**

| 维度       | URL / iframe                | SDK / 组件包                   |
| :--------- | :-------------------------- | :----------------------------- |
| 技术栈耦合 | 零，宿主只需 iframe 标签    | 高，产物需适配各宿主栈         |
| 隔离性     | 样式与 JS 运行时完全隔离    | 同一运行时，样式与全局状态互扰 |
| 部署耦合   | 独立发版，宿主零改动        | 升级需各宿主同步发版           |
| 交互深度   | 受限于 postMessage          | 直接函数调用与事件             |
| 会话与状态 | 独立上下文，凭证经 URL 传递 | 共享宿主上下文                 |

宿主异构且不可控，URL 是栈零耦合与独立发版下的必然选择，代价是交互深度受限、凭证传递依赖 URL。

**落地**

Vite 多入口构建实现独立集成页：每个入口为薄壳，复用 SPA 的业务组件与接口层，独立挂载运行。实例页面为用户所属业务网格的营销情况与改进建议。凭证链路：

1. 集成方调用我方后端接口换取 token；
2. token 拼接在集成 URL 传给页面；
3. 页面以 token 调用户信息查询接口，再以返回的用户信息请求业务数据。

```ts
// vite.config.ts（示意）：多入口，主应用与集成页各自产出独立 HTML
import { fileURLToPath, URL } from "node:url";
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    rollupOptions: {
      input: {
        main: fileURLToPath(new URL("./index.html", import.meta.url)),
        grid: fileURLToPath(new URL("./grid.html", import.meta.url)),
      },
    },
  },
});
```

```html
<!-- grid.html（示意）：集成页的独立薄壳，与主应用共享同一 bundle 依赖图 -->
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <title>网格营销</title>
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/entries/grid.ts"></script>
  </body>
</html>
```

```ts
// src/entries/grid.ts（当时的写法：启动序列在各入口各自实现）
import { createApp } from "vue";
import GridPage from "@/pages/GridPage.vue";
import { fetchUserInfo } from "@/api/user";
import { parseToken } from "@/lib/parseToken";
import { globalState } from "@/stores/global";

const token = parseToken(location.search);
if (token) {
  const user = await fetchUserInfo(token);
  globalState.value = { token, user };
  createApp(GridPage).mount("#app");
}
```

**局限与演进**

- 业务逻辑经 hooks 拆分后，集成页可直接复用视图组件与 hooks，重复实现的只剩装配层：重新引入并初始化全局状态对象（global.js，hooks 与业务模块从其中取值），「取 URL token → 初始化 → 挂载」的启动序列在每个入口重演，且 hooks 读取全局单例的时序是隐式契约——可收敛为共享 bootstrap （自举）模块，入口薄壳只负责调用与挂载；
- URL 形态的交互受限于 postMessage，若宿主可控且交互密集，SDK 形态的自然实现是 Web Components：产物与宿主栈解耦，同时支持属性传参与事件。

收敛形态如下（**演进方向示意，当时未落地**）：协议层下沉到骨架，页面通过参数传入，入口差异经钩子或返回实例续接。

```ts
// src/bootstrap.ts（演进方向示意）
import { createApp, type Component } from "vue";
import { fetchUserInfo } from "@/api/user";
import { parseToken } from "@/lib/parseToken";
import { globalState } from "@/stores/global";

interface BootstrapOptions {
  /** 入口特有的装配，时序由骨架保证 */
  beforeMount?: (app: ReturnType<typeof createApp>) => void | Promise<void>;
}

export async function bootstrap(
  page: Component,
  options: BootstrapOptions = {}
) {
  // 协议层：token 解析与鉴权兜底，各入口一致
  const token = parseToken(location.search);
  if (!token) {
    document.body.innerHTML = "<p>缺少访问凭证</p>";
    return;
  }

  const user = await fetchUserInfo(token);
  // 整体替换而非逐字段赋值，避免残留上一次会话
  globalState.value = { token, user };

  const app = createApp(page);
  await options.beforeMount?.(app);
  app.mount("#app");

  // 返回实例：装配差异较大的入口可继续 use / mount
  return app;
}
```

```ts
// src/entries/grid.ts（收敛后）
import { bootstrap } from "@/bootstrap";
import GridPage from "@/pages/GridPage.vue";

bootstrap(GridPage);
```

入口薄壳退化为一行调用，启动序列与 hooks 的时序依赖被封在骨架内部。

## 结语

这些实践围绕同一组约束展开：网络隔离催生平行测试目录（常态）与 Docker 镜像交付（特殊场景）两种测试形态，跨域与协议升级催生代理与自签证书，暴露面管控催生清单插件；测试体系、CI/CD 与对外集成是同一组约束在质量、发布与集成环节的延伸——前两者作为演进方向记录，后者以 Vite 多入口落地。工程化在这个项目里的价值不是引入新框架，而是在既定约束下把重复劳动自动化：联调零配置切换数据源、本地环境与线上协议一致、发版登记从手工整理变为构建的副产物、集成页以独立入口复用既有组件。
