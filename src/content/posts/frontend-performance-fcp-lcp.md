优化前首页 FCP（首次内容绘制）3.2 秒，LCP 超过 4 秒，弱网下首屏长时间白屏。最终 FCP 降到 1.1 秒、LCP 提升约 60%、主包体积减少 40%，核心接口 TP99 降到 150ms。这篇不堆 checklist，而是按我们实际的推进顺序复盘：**先测准，再按渲染链路从前到后逐层消除等待**。

## Table of contents

## 一、先建度量，拒绝"感觉变快了"

所有优化开始前先固定测量口径，否则改完无法归因：

- **实验室指标**：Lighthouse（CI 里跑，限定 throttling 配置）+ WebPageExposed 弱网模拟；
- **现场指标**：`web-vitals` 采集真实用户的 LCP / CLS / INP，按设备类型、网络类型分桶上报；
- **服务端指标**：接口打点看 TP50/TP99，区分"前端慢"和"接口慢"。

数据一拉，瓶颈非常清楚：白屏时间里，JS 下载执行占一半，首屏接口串行请求占另一半，LCP 元素是一张未优化的首屏图。

## 二、渲染链路：CSR → SSR 是最大单点收益

旧架构是纯 CSR：下载 JS → 执行 → 再发首屏请求 → 渲染。用户面对白屏的时间 = JS 链路 + 数据链路**串行相加**。

引入 SSR 后，首屏 HTML 在服务端带数据直出：

- 服务端在渲染前并行完成数据预取，HTML 到达浏览器时内容已经在里面，FCP 不再等 JS 加载完；
- 客户端注水（hydration）复用服务端注入的初始状态，首屏请求从客户端瀑布中消失；
- SEO 同步受益，列表页开始被搜索引擎正常收录。

SSR 不是免费的，配套要处理两件事：服务端渲染时禁用浏览器-only API（`window`/`document` 访问放到挂载后），以及静态页面边缘缓存（CDN 缓存渲染结果）。做完这一步，FCP 直接从 3.2s 降到 1.8s。

## 三、资源链路：预构建、懒加载与分包

剩下的 JS 链路按"少下载、晚下载、快解析"三招处理：

**1. Vite 依赖预构建**。裸模块导入（几百个 ESM 文件）在 dev 和冷启动时会形成请求瀑布，esbuild 预构建把依赖打成少量单文件；生产构建则把稳定依赖与业务代码分离。

**2. 路由级与组件级懒加载**，首屏只加载当前页代码：

```ts
const WorkOrder = () => import("@/views/WorkOrder.vue");
```

弹窗、图表、富文本编辑器这类重组件进一步延迟到交互时再加载。

**3. Rollup 手动分包**，避免默认策略下一个公共 chunk 变动导致全站缓存失效：

```ts
build: {
  rollupOptions: {
    output: {
      manualChunks: {
        "vendor-vue": ["vue", "vue-router", "pinia"],
        "vendor-utils": ["axios", "dayjs", "@vueuse/core"],
        "vendor-charts": ["echarts"], // 大库独立，按需页加载
      },
    },
  },
}
```

配合 `chunkSizeWarningLimit` 与产物分析（rollup-plugin-visualizer）持续盯防，主包体积减少 40%，且框架版本升级只动 vendor chunk，业务 chunk 的长效缓存不受影响。

**4. LCP 元素专项**：首屏图改 WebP/AVIF + `srcset` 响应式、`fetchpriority="high"`、预连接图片 CDN（`<link rel="preconnect">`），LCP 进一步收敛。

## 四、请求瀑布：BFF 聚合砍掉 80% 串行请求

首屏慢的另一半来自接口设计：页面要发 8–10 个请求（用户信息、权限、配置、列表、角标……），浏览器同域并发数有限，弱网下 RTT 被反复放大。

在 Node 层加 BFF 网关做**接口聚合与数据裁剪**：

- 一个页面对应一个聚合接口，服务端并行请求下游、裁剪掉页面用不到的字段，首屏串行请求数减少 80%；
- 鉴权、埋点、错误码转换在 BFF 统一处理，前端不再为每个后端服务写适配；
- 聚合层还成为缓存的天然挂载点（见下节）。

## 五、多级缓存：让 150ms 成为常态

BFF 之后接 Redis 多级缓存，按数据变化频率分三档：

| 数据类型             | 策略                                                         |
| -------------------- | ------------------------------------------------------------ |
| 用户权限、字典、配置 | 长 TTL + 主动失效，变更时发失效消息                          |
| 列表/统计快照        | 短 TTL（30–60s）+ stale-while-revalidate，先返旧值再后台刷新 |
| 强实时数据           | 不缓存，但通过 BFF 合并并发请求（singleflight）防击穿        |

缓存的关键不是"加 Redis"，而是**失效策略**：我们对配置类数据用"写后失效 + 版本号 key"，避免了脏数据；对热点列表用 SWR 保证接口永远快速返回。核心接口 TP99 最终稳定在 150ms。

## 六、静态资源发布策略

容易被忽视但收益巨大的一环：

- 带内容哈希的 JS/CSS/图片：`Cache-Control: public, max-age=31536000, immutable`，文件名即版本，永不过期；
- HTML：`Cache-Control: no-cache`，每次协商校验，保证用户永远拿到指向最新哈希资源的入口；
- 全站走 CDN，动态接口与静态资源域名分离，便于分别调优。

这正好解决了"发版后用户拿到新 HTML 但旧 chunk 已被 CDN 缓存"与"改一行代码整站缓存失效"两个老问题。

## 七、指标变化与方法论

| 优化项                     | 指标变化                              |
| -------------------------- | ------------------------------------- |
| SSR + 数据预取             | FCP 3.2s → 1.8s                       |
| 懒加载 + 分包 + LCP 图优化 | FCP → 1.1s，LCP 提升约 60%，主包 -40% |
| BFF 聚合                   | 首屏串行请求 -80%                     |
| Redis 多级缓存             | 核心接口 TP99 → 150ms                 |

回头看，方法论只有三句话：**用真实数据定位瓶颈而不是猜；按用户等待的关键路径（HTML→JS→数据→渲染）逐层消除串行等待；缓存与分包都要先想清楚失效边界**。性能不是一次性的冲刺，而是一条被度量守护的日常基线。
