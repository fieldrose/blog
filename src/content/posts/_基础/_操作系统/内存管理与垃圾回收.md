## Table of contents

> 本文属于 Mimas 个人技术博客（Astro 7 + TypeScript + Tailwind CSS 4，中英双语站点）的博客文章，项目语境见 `.trae/rules/doc-gen/00-context.md`。

JavaScript 不需要手动释放内存，不代表内存问题不存在。长时停留的 SPA、大列表、实时数据流都可能把内存推到临界点，表现为卡顿、崩溃或页面被系统回收。理解操作系统的内存管理与引擎的回收机制，才能判断泄漏发生在哪一层。本文以 Node 暴露的内存接口作为可观测入口，再映射到浏览器与 SPA 场景。

## 一、内存层次与虚拟内存

### 1.1 存储层次与局部性

| 层次 | 相对速度 | 容量 | 前端可见影响 |
| ---- | -------- | ---- | ------------ |
| 寄存器 | 最快 | 极小 | 引擎内部 |
| CPU 缓存 | 很快 | 小 | 连续内存访问更快 |
| 内存 | 中等 | 大 | 堆对象分配与 GC |
| 磁盘 / 闪存 | 慢 | 很大 | 资源加载、IndexedDB |

- 时间局部性：刚访问的数据很可能再次被访问。
- 空间局部性：访问某地址后，附近的地址很可能被访问。
- 数组顺序遍历比链表跳转快，主要原因是缓存命中率不同。
- 大对象与随机访问会破坏局部性，是运行时性能的隐性成本。

### 1.2 虚拟内存

- 每个进程拥有独立的虚拟地址空间，由 MMU 通过页表映射到物理内存。
- 分页把地址空间切成固定大小的页，常见页大小为 4KB。
- 访问未映射或已换出的页会触发缺页中断，由内核加载页面后恢复执行。
- TLB 缓存页表项，进程切换导致 TLB 失效，是进程切换昂贵的原因之一。
- 虚拟内存提供隔离、按需加载与内存超额分配能力。

### 1.3 栈与堆

- 栈保存函数调用帧，包含参数、局部变量与返回地址，分配释放由调用约定自动完成。
- 堆保存动态分配对象，生命周期不确定，需要垃圾回收或手动释放。
- 栈空间有限，深度递归会栈溢出；堆空间大但分配与回收有成本。
- JS 引擎会把部分对象分配在栈上或进行标量替换，但语义上仍按堆对象理解。

### 1.4 Node 的内存视图

Node 把进程内存拆成几个可查询字段，是理解堆内存与堆外内存最直接的入口。

```js
console.log(process.memoryUsage());
// { rss, heapTotal, heapUsed, external, arrayBuffers }
```

| 字段 | 含义 |
| ---- | ---- |
| `rss` | 进程常驻物理内存，包含堆、栈、代码段与共享库 |
| `heapTotal` | V8 申请到的堆总量 |
| `heapUsed` | V8 当前使用的堆量 |
| `external` | V8 管理的堆外内存 |
| `arrayBuffers` | `ArrayBuffer` 与 `Buffer` 占用的堆外内存 |

- `heapUsed` 持续上升且强制回收后不回落，才是泄漏信号。
- `rss` 长期高于预期可能来自 Buffer、原生插件或内存碎片，不一定是 JS 堆。
- Buffer 由 C++ 层分配，不计入 `heapUsed`，但计入 `external` 与 `arrayBuffers`。
- `Buffer.allocUnsafe` 从预分配池取内存，可能残留旧数据，使用前必须填充或覆写。
- `--max-old-space-size` 调整老生代上限，`--max-semi-space-size` 调整新生代大小。

```bash
node --max-old-space-size=4096 --trace-gc server.js
```

## 二、内存分配

### 2.1 分配策略与碎片

- 连续分配实现简单，但长期增删会产生外部碎片。
- 分页把内存切成固定块，消除外部碎片，但可能产生页内碎片。
- 伙伴系统按 2 的幂分配，合并相邻空闲块，操作系统与部分分配器使用。
- 内存碎片不会直接报错，表现为可用内存充足但无法满足大块分配。

### 2.2 V8 的内存布局

| 区域 | 内容 | 回收方式 |
| ---- | ---- | -------- |
| 新生代 | 新创建的短生命周期对象 | Scavenger 复制算法 |
| 老生代 | 存活较久的对象 | 标记清除与标记整理 |
| 大对象空间 | 超过阈值的大对象 | 随老生代回收 |
| 代码空间 | JIT 生成的机器码 | 特殊管理 |

- 新生代通常较小，分为两个半区，存活对象在两个半区之间复制。
- 对象经过多次回收仍存活会被晋升到老生代，晋升减少新生代复制成本。
- 老生代容量约 2–4GB 量级，具体受运行环境与参数影响，超过上限会触发 OOM。
- 大对象直接进入大对象空间，避免复制开销，但频繁创建大对象仍会造成压力。

## 三、垃圾回收

### 3.1 引用计数与标记清除

- 引用计数为每个对象维护引用数量，归零即回收，问题是无法处理循环引用。
- 标记清除从根集合出发标记可达对象，未被标记的即为垃圾，能处理循环引用。
- 标记整理在标记后把存活对象压缩到一端，消除碎片，但移动对象成本更高。
- 复制算法把存活对象复制到另一半空间，回收成本与存活对象数量成正比。

```ts
interface HeapObject {
  id: string;
  refs: HeapObject[];
}

function markSweep(roots: HeapObject[], heap: HeapObject[]): HeapObject[] {
  const reachable = new Set<HeapObject>();
  const stack = [...roots];

  while (stack.length) {
    const object = stack.pop()!;
    if (reachable.has(object)) continue;
    reachable.add(object);
    stack.push(...object.refs);
  }

  return heap.filter((object) => reachable.has(object));
}
```

- 模拟中的根可以是全局对象、当前调用栈上的引用、闭包捕获的变量。
- 真实实现还要处理写屏障、增量标记与并发标记，避免长时间暂停。
- 回收暂停会阻塞 JS 执行，长时间 GC 表现为卡顿或掉帧。

### 3.2 三色标记与增量回收

- 白色表示未访问，灰色表示已发现但子引用未处理，黑色表示已完全处理。
- 标记过程从根开始把对象染灰，处理完子引用后染黑。
- 增量标记把标记拆成多个小步骤，与 JS 执行交替进行，降低单次暂停。
- 并发标记在后台线程进行，需要写屏障记录对象引用的变化，保证不漏标。
- 并发与增量都有额外开销，回收器会在吞吐与延迟之间自适应调整。

### 3.3 V8 的回收流程

- Scavenger 负责新生代，采用复制算法，只复制存活对象，适合「大部分对象很快死亡」的分布。
- 老生代使用标记清除与标记整理，配合并行、增量与并发技术降低停顿。
- 空闲时间回收（Idle-time GC）利用浏览器空闲时段执行部分工作。
- 内存压力过大时会触发更激进的回收，频繁触发说明存在泄漏或分配过快。

### 3.4 弱引用

- `WeakMap`、`WeakSet` 的键是弱引用，不阻止回收。
- `WeakRef` 提供不阻止回收的对象引用，`deref()` 可能返回 `undefined`。
- `FinalizationRegistry` 可在对象被回收后执行清理回调，但回调时机不确定，不能用于关键逻辑。
- 弱引用适合缓存与关联数据，不能用于需要保证对象存活的场景。

### 3.5 Node 中的 GC 观测

```js
import v8 from "node:v8";
import { PerformanceObserver, constants } from "node:perf_hooks";

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.kind === constants.NODE_PERFORMANCE_GC_MAJOR) {
      console.log("major gc", entry.duration);
    }
  }
}).observe({ entryTypes: ["gc"] });

console.log(v8.getHeapStatistics().heap_size_limit);
```

- `--trace-gc` 输出每次回收的类型、耗时与前后堆大小，适合本地定位。
- `v8.getHeapStatistics()` 提供堆上限、已用空间与外部内存，适合上报监控。
- `v8.writeHeapSnapshot()` 生成快照，可用 Chrome DevTools 的 Memory 面板打开分析。
- `--inspect` 启动调试端口，DevTools 可实时查看对象分配与 GC 时间线。
- GC 条目来自 `perf_hooks`，可在生产环境低频采样上报。

## 四、内存泄漏与排查

### 4.1 常见泄漏模式

- 未解绑的事件监听与未清理的定时器，尤其挂在 `window` 或 `document` 上。
- 闭包持有大对象，函数长期存活导致引用无法释放。
- 全局变量或模块级缓存无上限，数据只进不出。
- 已移除 DOM 节点仍被 JS 引用，形成游离 DOM。
- 事件总线、观察者、订阅未取消，组件销毁后仍被回调引用。
- SPA 路由切换时组件实例、定时器、请求未销毁。

### 4.2 堆快照排查

1. 复现操作路径，先在干净状态拍一次快照；
2. 执行可疑操作若干次，再拍一次快照；
3. 使用 Comparison 视图对比两次快照的对象增量；
4. 查看 Retainers，确认对象被谁持有；
5. 定位到代码中的引用链后修复，再重复验证。

- Allocation instrumentation on timeline 可观察对象分配速率，适合定位持续增长的来源。
- 快照本身会暂停页面并占用内存，生产环境不能依赖。
- 内存增长不等于泄漏，缓存与数据结构扩容也会增长，需要区分「有上限的增长」与「无上限的增长」。

### 4.3 可观测指标

- 内存曲线是否呈阶梯式上升且不回落。
- GC 次数与耗时是否随运行时间增加。
- 页面崩溃率、渲染进程被杀率、低端机上的白屏率。
- `performance.memory` 仅部分浏览器提供，`performance.measureUserAgentSpecificMemory()` 需要跨域隔离。

### 4.4 Node 的泄漏排查

- 定时采样 `process.memoryUsage()`，观察 `heapUsed` 与 `rss` 的斜率，区分阶梯式增长与稳定平台。
- 使用 `--expose-gc` 手动调用 `global.gc()` 后再采样，排除尚未回收的噪声，生产环境不应开启。
- 在疑似泄漏前后调用 `v8.writeHeapSnapshot()`，对比快照中的对象增量与引用链。
- 常见来源：模块级缓存无上限、事件监听未移除、闭包持有请求上下文、连接与定时器未清理。
- 容器内存 limit 低于 V8 堆上限时会被 OOMKilled，`--max-old-space-size` 必须与 limit 留出余量。
- 内存压力往往先表现为事件循环延迟与 GC 耗时上升，监控应把两者放在一起看。

## 五、优化手段

- 为缓存设置容量上限与淘汰策略，避免只增不减。
- 大数组分块处理，及时释放不再需要的引用。
- 二进制数据使用 `ArrayBuffer` 与 `TypedArray`，避免大量小对象。
- 高频创建销毁的对象考虑对象池，但要评估复用带来的状态残留风险。
- 列表与图片使用分页、虚拟滚动与懒加载，控制同时在场的对象数量。
- 长任务结束后主动断开监听、清理定时器与订阅，把清理写进组件生命周期。
- Node 服务端处理大文件用流而不是 `readFile`，避免内存峰值等于文件大小。
- 长连接服务要限制单连接缓冲与并发数，防止慢客户端持续堆积数据。

内存问题的修复顺序是「先证明泄漏存在，再定位引用链，最后改代码」。没有快照对比的增长曲线只能说明可疑，不能说明原因。
