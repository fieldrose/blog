协议层决定请求能跑多快，请求层决定请求是否可控。重复提交、并发打满、弱网卡死、页面关闭丢失埋点，这些问题都能在封装层解决。本文给出可直接复用的 TypeScript 写法。

## 一、fetch 与 XHR

### 1.1 语义差异

| 能力 | fetch | XMLHttpRequest |
| ---- | ----- | -------------- |
| 返回值 | Promise | 事件回调 |
| HTTP 错误 | 4xx/5xx 仍 resolve | 触发 load，需看 status |
| 取消 | AbortSignal | `abort()` |
| 上传进度 | 支持有限 | `upload.onprogress` |
| 下载进度 | 通过流读取 | `onprogress` |
| 流式响应 | `response.body` | 不支持 |
| Cookie 默认 | 同源携带 | 同源携带 |

```ts
const response = await fetch("/api/orders", { method: "GET" });

if (!response.ok) {
  // fetch 只在网络失败或中断时 reject，HTTP 错误需要手动判断
  throw new Error(`HTTP ${response.status}`);
}

const data = await response.json();
```

- `fetch` 的 Promise 只在网络故障、跨域失败或主动中断时 reject。
- 需要手动检查 `response.ok` 或 `response.status`。
- 跨域携带 Cookie 必须显式设置 `credentials: "include"`。
- `fetch` 默认不带 `Referer` 之外的额外凭证，也不会自动重试。

### 1.2 流式响应与进度

```ts
const response = await fetch("/api/export");
if (!response.body) throw new Error("stream unavailable");

const reader = response.body.getReader();
const decoder = new TextDecoder();
let text = "";

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  text += decoder.decode(value, { stream: true });
}
```

- 流式读取适合大文件、SSE、逐块渲染的导出结果。
- 读取速度由消费端控制，形成天然背压。
- `TextDecoder` 需要 `{ stream: true }` 处理跨块的半个多字节字符。
- 上传进度在 `fetch` 中支持有限，需要精确进度时使用 XHR。

### 1.3 页面关闭时的请求

```ts
window.addEventListener("pagehide", () => {
  const body = JSON.stringify({ type: "leave", at: Date.now() });
  navigator.sendBeacon("/api/telemetry", body);
});
```

- `sendBeacon` 不阻塞页面卸载，适合埋点与日志，失败无回调。
- `fetch` 配合 `keepalive: true` 也能在卸载后继续发送，但请求体有大小限制。
- 不应在 `unload` 事件中做异步请求，移动端与 bfcache 场景下不可靠。
- 关键业务数据不要依赖卸载时上报，应在操作发生时立即发送。

## 二、请求封装

### 2.1 超时与取消

```ts
interface RequestOptions extends RequestInit {
  timeout?: number;
}

async function request(input: RequestInfo | URL, options: RequestOptions = {}): Promise<Response> {
  const { timeout = 8000, signal, ...init } = options;
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(new DOMException("timeout", "TimeoutError")), timeout);

  const combined = signal ? AbortSignal.any([signal, controller.signal]) : controller.signal;

  try {
    return await fetch(input, { ...init, signal: combined });
  } finally {
    clearTimeout(timer);
  }
}
```

- 超时用 `AbortController` 实现，避免请求悬挂占用连接。
- `AbortSignal.any` 可合并多个取消源，旧环境需要手动转发 `abort` 事件。
- 区分「用户取消」与「超时」：前者不应提示错误，后者应给出重试入口。
- 组件卸载时应取消未完成请求，避免回调更新已销毁的视图。

### 2.2 重试与退避

```ts
interface RetryOptions {
  attempts?: number;
  baseDelay?: number;
  maxDelay?: number;
}

async function retry<T>(task: () => Promise<T>, options: RetryOptions = {}): Promise<T> {
  const { attempts = 3, baseDelay = 300, maxDelay = 5000 } = options;

  for (let attempt = 0; attempt < attempts; attempt++) {
    try {
      return await task();
    } catch (error) {
      if (attempt === attempts - 1) throw error;
      const exp = Math.min(maxDelay, baseDelay * 2 ** attempt);
      const jitter = Math.random() * exp * 0.3; // 打散重试峰值
      await new Promise((resolve) => setTimeout(resolve, exp + jitter));
    }
  }

  throw new Error("unreachable");
}
```

- 只对幂等请求或带幂等键的请求重试，POST 无条件重试会造成重复写入。
- 指数退避加随机抖动，避免服务端故障时所有客户端同时重试。
- 服务端返回 `Retry-After` 时应优先遵循。
- 4xx 中的参数错误、鉴权失败不应重试，5xx 与网络错误才值得重试。

### 2.3 请求去重

```ts
const inflight = new Map<string, Promise<Response>>();

function requestOnce(key: string, init: () => Promise<Response>): Promise<Response> {
  const existing = inflight.get(key);
  if (existing) return existing;

  const promise = init().finally(() => inflight.delete(key));
  inflight.set(key, promise);
  return promise;
}
```

- 去重键由 URL、方法、关键参数决定，不能只用 URL。
- 同一时刻的重复请求共享同一个 Promise，避免接口被打爆。
- 请求结束后必须清理，否则失败结果会被永久缓存。
- 去重解决的是并发重复，缓存解决的是时间维度重复，两者需要分别设计。

### 2.4 并发池

```ts
async function requestPool<T, R>(
  items: T[],
  limit: number,
  worker: (item: T) => Promise<R>,
): Promise<R[]> {
  const results = new Array<R>(items.length);
  let cursor = 0;

  const runners = Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (cursor < items.length) {
      const index = cursor++;
      results[index] = await worker(items[index]);
    }
  });

  await Promise.all(runners);
  return results;
}
```

- 并发数要结合域名并发限制与服务端承载能力设置。
- 结果按原顺序写入，避免调用方再做排序。
- 单个任务失败时，需要决定是整体失败还是跳过，不能默认吞掉错误。
- 上传、图片加载、批量数据拉取都可以复用这一模型。

## 三、上传与下载

### 3.1 分片上传与断点续传

```ts
async function uploadFile(file: File, chunkSize = 5 * 1024 * 1024): Promise<void> {
  for (let offset = 0; offset < file.size; offset += chunkSize) {
    const chunk = file.slice(offset, offset + chunkSize);
    const response = await fetch(`/api/upload?offset=${offset}`, {
      method: "PUT",
      body: chunk,
      headers: { "Content-Type": "application/octet-stream" },
    });
    if (!response.ok) throw new Error(`chunk ${offset} failed`);
  }
}
```

- 分片大小要在请求数与单次传输时间之间取平衡。
- 每片请求必须可重试且幂等，服务端按偏移写入。
- 断点续传需要服务端提供已上传分片列表，客户端跳过已完成部分。
- 分片完成后由服务端合并，合并前要做完整性校验。
- 并发上传可提高吞吐，但要控制并发数，避免拥塞窗口被压垮。

### 3.2 下载与进度

- `Content-Length` 存在时可以计算下载百分比。
- 大文件优先使用流式读取，边下边处理，避免一次性占用大量内存。
- 需要断点续传时使用 `Range: bytes=start-`，服务端返回 206 与 `Content-Range`。
- 下载失败时记录已完成的字节数，下次从断点继续。
- 文件校验放在服务端或使用哈希比对，不能只依赖大小。

## 四、实时通信

| 方案 | 方向 | 连接 | 适用 |
| ---- | ---- | ---- | ---- |
| 短轮询 | 客户端拉取 | 每次新建或复用 | 低频、实现简单 |
| 长轮询 | 客户端拉取 | 挂起至有数据 | 兼容性要求高 |
| SSE | 服务端推送 | 单条 HTTP 长连接 | 通知、日志、进度 |
| WebSocket | 双向 | 独立长连接 | 聊天、协同、游戏 |

- SSE 基于 `text/event-stream`，浏览器自动重连并通过 `Last-Event-ID` 续传。
- WebSocket 通过 HTTP Upgrade 握手，之后使用独立帧协议，双向低延迟。
- 长连接需要心跳与超时检测，移动网络切换后要主动重连。
- 重连采用指数退避并设置上限，避免服务端故障时形成重连风暴。
- 实时消息要处理乱序、重复与断线期间的数据补偿。

## 五、缓存与离线

- HTTP 缓存是协议层，适用于所有请求，受响应头控制。
- Service Worker 缓存位于请求拦截层，可按资源类型自定义策略。
- 内存缓存适合会话内的接口数据，需要容量上限与 TTL。
- 常见策略：静态资源 Cache First，接口 Network First，配置类 Stale While Revalidate。
- 离线场景要区分「无网络」与「有网络但请求失败」，前者读缓存，后者按策略重试。
- 缓存版本与清理策略必须显式设计，否则旧数据会长期滞留。

## 六、监控与弱网

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as PerformanceResourceTiming[]) {
    if (entry.initiatorType !== "fetch" && entry.initiatorType !== "xmlhttprequest") continue;

    report({
      url: entry.name,
      duration: entry.duration,
      transferSize: entry.transferSize,
      protocol: entry.nextHopProtocol,
    });
  }
}).observe({ type: "resource", buffered: true });
```

- 关注成功率、P75/P95 耗时、传输体积与协议版本，而不是只看平均值。
- 按接口、设备档位、网络类型、版本分桶，才能定位长尾。
- `navigator.connection` 在 Chromium 可用，Safari 不支持，需提供默认策略。
- 弱网下降低并发、延长超时、优先读缓存，并给出明确的加载状态。
- 监控上报本身要异步、采样、限流，不能反过来拖慢业务请求。

## 七、排查清单

- 请求是否被预检、是否携带了不必要的 Cookie 与自定义头。
- 是否存在重复请求、串行瀑布或未取消的过期请求。
- 超时与重试是否区分了错误类型，是否会放大故障。
- 上传下载是否一次性读入内存，是否支持断点。
- 长连接是否有心跳、重连与补偿机制。
- 缓存策略是否区分静态资源与接口，是否有版本与清理方案。
